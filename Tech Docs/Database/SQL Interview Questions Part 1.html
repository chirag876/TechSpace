1. Indexes

Basic

Q1. What is an index in SQL?

An index is a database object that improves the speed of data retrieval on a table. It works like an index in a book — instead of scanning every row, the database engine can jump directly to the relevant data.

CREATE INDEX idx_employee_name ON Employees(Name);

Q2. What are the types of indexes in SQL?

Type Description
Clustered Physically sorts rows in the table. Only 1 per table.
Non-Clustered Separate structure with pointers to rows. Multiple allowed.
Unique Ensures no duplicate values in the indexed column.
Composite Index on two or more columns.
Full-Text For searching text data (LIKE ‘%…%’ alternatives).
Filtered Index on a subset of rows (WHERE clause on index).
Covering Index that includes all columns needed by a query.
Spatial For geographic/spatial data types.
XML For XML data type columns.

Q3. What is the difference between a Clustered and Non-Clustered index?

Feature Clustered Non-Clustered
Physical order Sorts actual table data Separate structure
Count per table Only 1 Up to 999 (SQL Server)
Leaf level Actual data rows Row pointers (RID or Clustered Key)
Speed for range scan Faster Slightly slower
Storage No extra storage Extra storage required 
-- Clustered (usually created with PRIMARY KEY)
CREATE CLUSTERED INDEX idx_emp_id ON Employees(EmpID);

-- Non-Clustered
CREATE NONCLUSTERED INDEX idx_emp_name ON Employees(Name);

Q4. Can a table have no clustered index? What is such a table called?

Yes. A table without a clustered index is called a Heap. Data is stored in an unordered structure. INSERTs are fast but SELECT/range queries are slow.

Q5. How do you create a Unique index?

CREATE UNIQUE INDEX idx_unique_email ON Employees(Email);
-- Prevents duplicate emails; allows NULL (one NULL typically)

Q6. How do you drop an index?

-- SQL Server
DROP INDEX idx_employee_name ON Employees;

-- MySQL
DROP INDEX idx_employee_name ON Employees;
-- OR
ALTER TABLE Employees DROP INDEX idx_employee_name;

Intermediate

Q7. What is a Composite Index and what is column order significance?

A composite index is built on multiple columns. Column order matters — the index is used when the query filters on the leading (leftmost) columns.

CREATE INDEX idx_dept_name ON Employees(DepartmentID, Name);

-- Uses index 
SELECT * FROM Employees WHERE DepartmentID = 5 AND Name = 'Rahul';

-- Uses index (partial) 
SELECT * FROM Employees WHERE DepartmentID = 5;

-- Does NOT use index  (leading column missing)
SELECT * FROM Employees WHERE Name = 'Rahul';

Q8. What is a Covering Index?

An index that includes all columns referenced in the query (SELECT, WHERE, JOIN, ORDER BY). The query engine satisfies the query entirely from the index without touching the base table — called an Index-Only Scan.

-- Query
SELECT Name, Salary FROM Employees WHERE DepartmentID = 3;

-- Covering index for above query
CREATE INDEX idx_covering ON Employees(DepartmentID) INCLUDE (Name, Salary);
-- INCLUDE columns are stored at leaf level but not key level

Q9. What is an Index Scan vs Index Seek?

Index Seek Index Scan
How Navigates B-Tree to exact row(s) Reads all index entries
Performance Fast (selective) Slow (like table scan)
When Equality / range with good selectivity Poor selectivity or no WHERE
Preferred Yes Avoid

You can see these in Execution Plans. Always aim for Index Seek.

Q10. What is a Filtered Index?

An index created on a subset of rows defined by a WHERE clause. Smaller and more efficient when queries often filter on a specific value.

-- Only index active employees
CREATE INDEX idx_active_emp ON Employees(Name)
WHERE IsActive = 1;

Q11. What happens internally when you create a Clustered Index?

SQL Server physically reorders all the data pages of the table to match the index key order. The leaf level of the B-Tree is the actual data. That’s why only one clustered index per table is allowed.

Q12. What is Index Fragmentation? How do you fix it?

As rows are inserted/updated/deleted, index pages split or become partially filled — this is fragmentation. It leads to extra I/O and slower reads.

-- Check fragmentation (SQL Server)
SELECT index_id, avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('Employees'), NULL, NULL, 'LIMITED');

-- < 10%  → No action needed
-- 10–30% → REORGANIZE (online, light)
-- > 30%  → REBUILD (heavier, can be offline)

ALTER INDEX idx_emp_name ON Employees REORGANIZE;
ALTER INDEX idx_emp_name ON Employees REBUILD;
ALTER INDEX ALL ON Employees REBUILD;

Q13. What is a Fill Factor?

Fill Factor tells SQL Server how full to make each index page during a build/rebuild. A value of 80 means 80% full, leaving 20% for future inserts without page splits.

CREATE INDEX idx_name ON Employees(Name) WITH (FILLFACTOR = 80);

Low fill factor → Less fragmentation, more storage.
High fill factor → More storage efficient, more fragmentation over time.

Advanced

Q14. How does a B-Tree index work internally?

Most SQL indexes use a B+ Tree structure:

  • Root node → Branch nodes → Leaf nodes
  • Leaf nodes contain the actual indexed key + pointer (or the data row for clustered)
  • All leaf nodes are doubly linked for efficient range scans
  • Searching is O(log N)
  • Insertions may cause page splits, leading to fragmentation

Q15. What is the difference between INCLUDE columns and key columns in an index?

Aspect Key Columns INCLUDE Columns
Part of B-Tree structure Yes No (leaf level only)
Used for search/sort Yes No
Used to cover queries Yes Yes
Max size limit 900 bytes (SQL Server) No key limit 
-- DepartmentID is key (searchable), Name & Salary are included (coverable)
CREATE INDEX idx_dept ON Employees(DepartmentID) INCLUDE(Name, Salary);

Q16. What are invisible/disabled indexes? When would you use them?

-- Disable an index (SQL Server) — structure exists, not maintained
ALTER INDEX idx_name ON Employees DISABLE;

-- Re-enable
ALTER INDEX idx_name ON Employees REBUILD;

Used when you want to test query performance without an index without dropping it.

Q17. How does an index affect INSERT, UPDATE, DELETE performance?

Every DML operation must also update the index. More indexes = slower writes.

  • INSERT → Adds new entry to all indexes
  • DELETE → Removes entry from all indexes
  • UPDATE → Deletes old entry + inserts new entry in affected indexes

Rule: Over-indexing hurts write-heavy tables. Index only what you query.

Q18. What is an Index Intersection?

When SQL Server uses two separate indexes on a single table and merges (intersects) the results to satisfy a query with multiple WHERE conditions. Less efficient than a covering index but better than a full table scan.

Q19. Commonly ignored — What is a Non-Clustered index on a Heap vs on a Clustered table?

Scenario Leaf Level Pointer
Heap (no clustered index) Row Identifier (RID) — 8-byte file:page:slot
Has Clustered Index Clustered index key value

If you later add a clustered index on a heap, all non-clustered indexes are automatically rebuilt because their pointers change from RID to the cluster key.

Q20. Commonly ignored — What is a Reverse Key Index?

Used in Oracle. Reverses the bytes of the index key to avoid right-hand-side contention in B-Trees when inserting sequential values (e.g., auto-increment IDs). Not available in SQL Server natively.

2. DELETE vs DROP vs TRUNCATE

Basic

Q1. What is the difference between DELETE, DROP, and TRUNCATE?

Feature DELETE TRUNCATE DROP
Type DML DDL (in most DBs) DDL
Removes Rows (filtered or all) All rows Entire table/object
WHERE clause Supported Not supported N/A
Rollback Yes (within transaction) Yes (SQL Server) / MySQL No (in most DBs)
Triggers fired Yes No No
Resets identity/auto-inc No Yes N/A
Space reclaimed No (pages marked) Yes Yes
Logged Fully logged Minimally logged Minimally logged

Q2. When should you use DELETE over TRUNCATE?

Use DELETE when:

  • You need to remove specific rows using a WHERE clause
  • You need triggers to fire (e.g., audit logging on row deletion)
  • You need the operation to be easily rollbackable in an existing transaction
  • You need to cascade deletes via FK constraints

Q3. Can TRUNCATE be rolled back?

SQL Server: Yes — if inside an explicit BEGIN TRANSACTION
MySQL/PostgreSQL: Yes — TRUNCATE is transactional
Oracle: No — TRUNCATE is auto-committed and cannot be rolled back

BEGIN TRANSACTION;
TRUNCATE TABLE Employees;
ROLLBACK; -- Works in SQL Server, data is restored

Q4. Can you use TRUNCATE on a table that has a Foreign Key constraint?

No — you cannot TRUNCATE a table that is referenced by a FK from another table, even if the child table is empty.

-- Will fail if Orders references Customers via FK
TRUNCATE TABLE Customers; --  Error

-- You must either:
-- 1. DROP the FK constraint first, then TRUNCATE, then recreate FK
-- 2. Or DELETE instead

Intermediate

Q5. How does DELETE work internally vs TRUNCATE?

DELETE:

  • Scans rows (index seek or table scan)
  • Logs each deleted row individually in the transaction log
  • Does not release pages back to OS (space marked as reusable)
  • Row-level locking

TRUNCATE:

  • Deallocates entire data pages — logs only page deallocations
  • Much faster — O(1) vs O(N)
  • Table-level lock
  • Resets identity counter

Q6. Can DELETE fire triggers? Can TRUNCATE?

-- DELETE fires AFTER DELETE triggers 
DELETE FROM Employees WHERE DeptID = 5;

-- TRUNCATE does NOT fire row-level triggers 
TRUNCATE TABLE Employees;

This is a critical behavioral difference — audit trails relying on triggers will miss TRUNCATE operations.

Q7. What happens to identity columns after DELETE vs TRUNCATE?

CREATE TABLE Test (ID INT IDENTITY(1,1), Name VARCHAR(50));
INSERT INTO Test VALUES ('A'), ('B'), ('C');

DELETE FROM Test;
INSERT INTO Test VALUES ('D');
-- ID will be 4 (identity continues from last value)

TRUNCATE TABLE Test;
INSERT INTO Test VALUES ('D');
-- ID will be 1 (identity resets to seed)

Q8. How do you reset identity after DELETE without TRUNCATE?

-- SQL Server
DBCC CHECKIDENT ('Employees', RESEED, 0);

-- MySQL
ALTER TABLE Employees AUTO_INCREMENT = 1;

Q9. What is the difference between DROP TABLE and DROP DATABASE?

DROP TABLE Employees;       -- Removes the table structure + all data + indexes
DROP DATABASE CompanyDB;    -- Removes the entire database + all objects inside

Q10. Commonly ignored — Can you DELETE from a table using a JOIN?

-- SQL Server
DELETE e
FROM Employees e
INNER JOIN Departments d ON e.DeptID = d.DeptID
WHERE d.DeptName = 'HR';

-- MySQL
DELETE e FROM Employees e
JOIN Departments d ON e.DeptID = d.DeptID
WHERE d.DeptName = 'HR';

Q11. Commonly ignored — What is a Soft Delete?

Instead of physically deleting rows, a column like IsDeleted BIT or DeletedAt DATETIME is used. The row stays in the DB but is filtered in all queries.

-- Soft delete
UPDATE Employees SET IsDeleted = 1, DeletedAt = GETDATE() WHERE EmpID = 101;

-- Query filters it out
SELECT * FROM Employees WHERE IsDeleted = 0;

Common in audit-heavy systems, SaaS apps, and anywhere data recovery is needed.

Advanced

Q12. How do you DELETE large volumes of data efficiently without blocking?

Deleting millions of rows in one DELETE statement causes:

  • Huge transaction log growth
  • Long-running locks blocking other queries
-- Batch delete approach (SQL Server)
DECLARE @BatchSize INT = 10000;
DECLARE @Deleted INT = 1;

WHILE @Deleted > 0
BEGIN
    DELETE TOP (@BatchSize) FROM Orders WHERE OrderDate < '2020-01-01';
    SET @Deleted = @@ROWCOUNT;
    WAITFOR DELAY '00:00:01'; -- Small pause to release locks
END

Q13. What is TRUNCATE with a partition?

-- SQL Server 2016+
-- Truncate only a specific partition without affecting others
TRUNCATE TABLE SalesData WITH (PARTITIONS (1, 3));

Q14. Commonly ignored — What happens to indexes and statistics after TRUNCATE?

  • Indexes are kept (not dropped)
  • Index statistics are reset to zero because all data is gone
  • The index structure is intact but empty

Q15. Commonly ignored — DROP TABLE vs TRUNCATE on temp tables?

-- For #TempTable in stored procedures:
TRUNCATE TABLE #TempTable; -- Keeps structure, clears data (reuse in loops)
DROP TABLE #TempTable;     -- Removes structure entirely

TRUNCATE on a temp table inside a loop is much more efficient than DROP + CREATE.

3. SQL Optimization

Basic

Q1. What is SQL query optimization?

The process of writing or restructuring SQL queries to reduce execution time, CPU usage, memory, and I/O — making them run faster and more efficiently.

Q2. What is an Execution Plan?

A visual/textual roadmap showing how SQL Server executes a query — which indexes it uses, join types, estimated rows, cost percentages.

-- View estimated plan (no execution)
SET SHOWPLAN_ALL ON;

-- View actual plan after execution
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- In SSMS: Ctrl+M → Include Actual Execution Plan

*Q3. Why should you avoid SELECT ?

  • Returns unnecessary columns → more network I/O
  • Prevents covering index usage (optimizer can’t use index-only scan)
  • Breaks code if table schema changes
-- Bad 
SELECT * FROM Employees WHERE DeptID = 3;

-- Good 
SELECT EmpID, Name, Salary FROM Employees WHERE DeptID = 3;

Q4. What is the N+1 query problem?

When code executes 1 query to fetch N records, then N additional queries for related data — instead of a single JOIN.

-- N+1 problem (in application code)
-- 1 query: SELECT * FROM Orders  → returns 100 orders
-- 100 queries: SELECT * FROM Customers WHERE ID = ? (for each order)

-- Fix: Single query with JOIN
SELECT o.OrderID, c.Name FROM Orders o
JOIN Customers c ON o.CustomerID = c.CustomerID;

Intermediate

Q5. What makes a query SARGable?

SARG = Search ARGument. A SARGable predicate is one where the query engine can use an index seek rather than a scan.

-- NOT SARGable  (function on column disables index usage)
SELECT * FROM Employees WHERE YEAR(HireDate) = 2022;
SELECT * FROM Employees WHERE UPPER(Name) = 'RAHUL';
SELECT * FROM Employees WHERE Salary + 500 > 50000;

-- SARGable 
SELECT * FROM Employees WHERE HireDate >= '2022-01-01' AND HireDate < '2023-01-01';
SELECT * FROM Employees WHERE Name = 'Rahul';  -- case-insensitive by default collation
SELECT * FROM Employees WHERE Salary > 49500;

Q6. How do implicit type conversions affect performance?

-- Column EmpCode is VARCHAR, passing INT
SELECT * FROM Employees WHERE EmpCode = 12345;
-- SQL Server applies CONVERT on every row → index not used 

-- Fix: match data types
SELECT * FROM Employees WHERE EmpCode = '12345'; --

Q7. What is the difference between EXISTS and IN for subqueries?

-- IN — evaluates entire subquery result set
SELECT * FROM Employees WHERE DeptID IN (SELECT DeptID FROM Departments WHERE Location = 'Jaipur');

-- EXISTS — stops at first match (short-circuit)
SELECT * FROM Employees e WHERE EXISTS (
    SELECT 1 FROM Departments d WHERE d.DeptID = e.DeptID AND d.Location = 'Jaipur'
);
  • EXISTS is generally faster for large datasets — short-circuits on first match
  • IN can be slow if subquery returns NULL values (entire result becomes NULL-unsafe)

Q8. How does NOT IN differ from NOT EXISTS with NULLs?

-- If subquery returns any NULL, NOT IN returns zero rows!
SELECT * FROM A WHERE ID NOT IN (SELECT ID FROM B);
-- If B has even one NULL → result is empty 

-- NOT EXISTS handles NULLs correctly 
SELECT * FROM A WHERE NOT EXISTS (SELECT 1 FROM B WHERE B.ID = A.ID);

This is a very common bug in production code!

Q9. What is the impact of using DISTINCT vs GROUP BY?

-- Both deduplicate, but GROUP BY is used with aggregates
SELECT DISTINCT DeptID FROM Employees;
SELECT DeptID FROM Employees GROUP BY DeptID;

-- Performance: Similar, but DISTINCT may be slightly faster for simple dedup
-- GROUP BY preferred when combining with COUNT, SUM, etc.

Q10. What are statistics and why do they matter for optimization?

Statistics are histograms maintained by the database engine about column value distribution. The Query Optimizer uses them to estimate row counts and choose the best execution plan.

-- View statistics for a table
DBCC SHOW_STATISTICS ('Employees', idx_emp_dept);

-- Update statistics
UPDATE STATISTICS Employees;
UPDATE STATISTICS Employees idx_emp_dept;

-- Auto-update stats may lag on large tables — manually update in scheduled jobs

Q11. What is Parameter Sniffing?

SQL Server caches the execution plan for the first execution of a stored procedure. If the plan was generated for atypical parameters, subsequent calls with different parameters use a suboptimal cached plan.

-- Problem: First call with DeptID = 1 (10 rows) → cached plan does index seek
-- Second call with DeptID = 99 (500,000 rows) → plan is wrong → slow table scan happens anyway

-- Solutions:
-- 1. OPTION (RECOMPILE) — recompile each time (CPU cost)
EXEC GetEmployeesByDept @DeptID = 99 WITH RECOMPILE;

-- 2. OPTIMIZE FOR
SELECT * FROM Employees WHERE DeptID = @DeptID
OPTION (OPTIMIZE FOR (@DeptID = 5));

-- 3. OPTIMIZE FOR UNKNOWN
OPTION (OPTIMIZE FOR (@DeptID UNKNOWN));

-- 4. Use local variables (breaks sniffing)
DECLARE @LocalDept INT = @DeptID;
SELECT * FROM Employees WHERE DeptID = @LocalDept;

Q12. What is a Table Variable vs Temp Table vs CTE for performance?

Table Variable (@t) Temp Table (#t) CTE
Statistics No Yes N/A
Indexes Limited (only PK/Unique) Full indexes N/A
Scope Current batch Session Current query only
Transaction log Minimal More logging N/A
Good for Small datasets Large datasets Readability / recursion
Spill to tempdb Sometimes Yes N/A

Q13. What is a Hash Join, Nested Loop, and Merge Join?

Join Type Best For Notes
Nested Loop Small outer, indexed inner O(N*M) worst case
Hash Join Large unindexed datasets Uses memory; spills to disk if large
Merge Join Both sides sorted/indexed Fastest when pre-sorted

Optimizer chooses automatically. You can force with hints (not recommended in production):

SELECT * FROM A INNER MERGE JOIN B ON A.ID = B.ID;
SELECT * FROM A INNER HASH JOIN B ON A.ID = B.ID;
SELECT * FROM A INNER LOOP JOIN B ON A.ID = B.ID;

Advanced

Q14. What is query plan caching and plan reuse?

SQL Server caches compiled plans in the Plan Cache. Plans are reused when the query text matches exactly (including whitespace and case for ad-hoc queries). Parameterized queries or stored procedures reuse plans more reliably.

-- View plan cache
SELECT usecounts, size_in_bytes, text
FROM sys.dm_exec_cached_plans
CROSS APPLY sys.dm_exec_sql_text(plan_handle);

-- Clear plan cache (dev only!)
DBCC FREEPROCCACHE;

Q15. Commonly ignored — What is a Key Lookup and how to eliminate it?

A Key Lookup happens when a non-clustered index satisfies the WHERE clause but doesn’t cover all columns in SELECT. SQL Server must do a second lookup into the clustered index for the remaining columns.

-- Index on DeptID only
-- Query: SELECT Name, Salary FROM Employees WHERE DeptID = 3
-- → Index seek on DeptID  + Key Lookup for Name/Salary  (expensive for many rows)

-- Fix: Add INCLUDE columns
CREATE INDEX idx_dept_cover ON Employees(DeptID) INCLUDE(Name, Salary);

Q16. Commonly ignored — What are Row Estimates and why do they matter?

The optimizer picks join order and join type based on estimated row counts. If stats are stale, estimates are wrong → bad plans.

-- Check actual vs estimated rows in execution plan
-- Huge discrepancy (e.g., estimated 1 row, actual 500,000) → stale statistics

-- Fix: Update stats or use trace flag 2371 for dynamic stats threshold

Q17. What are Query Hints and when should you use them?

-- Force index
SELECT * FROM Employees WITH (INDEX(idx_emp_dept)) WHERE DeptID = 3;

-- No lock
SELECT * FROM Employees WITH (NOLOCK) WHERE DeptID = 3;

-- Recompile
SELECT * FROM Employees WHERE DeptID = @id OPTION (RECOMPILE);

-- Max degree of parallelism
SELECT * FROM LargeTable OPTION (MAXDOP 1); -- Single threaded

Hints bypass the optimizer. Use only when you’ve proven via testing that the optimizer consistently makes the wrong choice.

Q18. Commonly ignored — How does OR impact index usage?

-- OR often prevents index usage 
SELECT * FROM Employees WHERE DeptID = 3 OR Name = 'Rahul';

-- Fix: UNION ALL (each part can use its own index) 
SELECT * FROM Employees WHERE DeptID = 3
UNION ALL
SELECT * FROM Employees WHERE Name = 'Rahul' AND DeptID <> 3;

Q19. What is a Parallel Query Plan and when does it kick in?

SQL Server uses parallelism (multiple CPU cores) for large queries when the estimated cost exceeds the Cost Threshold for Parallelism (default: 5). Controlled by MAXDOP setting.

-- Check/set MAXDOP
SELECT value_in_use FROM sys.configurations WHERE name = 'max degree of parallelism';

-- Disable parallelism at query level
SELECT * FROM BigTable OPTION (MAXDOP 1);

Q20. Commonly ignored — How do window functions compare to GROUP BY for performance?

-- Less efficient: Self-join or subquery to get dept avg
SELECT e.Name, e.Salary,
    (SELECT AVG(Salary) FROM Employees WHERE DeptID = e.DeptID) AS AvgSalary
FROM Employees e;

-- More efficient: Window function (single pass)
SELECT Name, Salary,
    AVG(Salary) OVER (PARTITION BY DeptID) AS AvgSalary
FROM Employees;

Window functions process in one table scan instead of multiple subquery executions.

4. Stored Procedures

Basic

Q1. What is a Stored Procedure?

A stored procedure is a precompiled set of SQL statements stored in the database. It can accept parameters, perform logic, and return results.

CREATE PROCEDURE GetEmployeesByDept
    @DeptID INT
AS
BEGIN
    SELECT EmpID, Name, Salary
    FROM Employees
    WHERE DeptID = @DeptID;
END;

-- Execute
EXEC GetEmployeesByDept @DeptID = 3;

Q2. What are the advantages of Stored Procedures?

  • Performance: Plan is compiled and cached on first run
  • Security: Users execute SP without direct table access
  • Reduced network traffic: Multiple statements in one call
  • Maintainability: Logic centralized in DB
  • Reusability: Call from multiple applications

Q3. What is the difference between a Stored Procedure and a Function?

Feature Stored Procedure Function (UDF)
Return value Optional (OUT params, result sets) Mandatory (scalar or table)
Use in SELECT Cannot be used directly Scalar UDFs can
DML operations Full DML allowed Limited (no INSERT/UPDATE/DELETE on base tables in scalar UDF)
Transaction control Yes Limited
Error handling TRY-CATCH Limited
Side effects Allowed Not allowed (pure)

Q4. What are input and output parameters in a stored procedure?

CREATE PROCEDURE GetEmployeeCount
    @DeptID INT,                    -- Input parameter
    @EmpCount INT OUTPUT            -- Output parameter
AS
BEGIN
    SELECT @EmpCount = COUNT(*)
    FROM Employees
    WHERE DeptID = @DeptID;
END;

-- Usage
DECLARE @Count INT;
EXEC GetEmployeeCount @DeptID = 3, @EmpCount = @Count OUTPUT;
PRINT @Count;

Q5. What is the difference between EXEC and sp_executesql?

-- EXEC (string concatenation — risky)
DECLARE @SQL NVARCHAR(500) = 'SELECT * FROM ' + @TableName;
EXEC (@SQL); --  SQL Injection risk, no plan reuse

-- sp_executesql (parameterized — safe)
DECLARE @SQL NVARCHAR(500) = N'SELECT * FROM Employees WHERE DeptID = @DeptID';
EXEC sp_executesql @SQL, N'@DeptID INT', @DeptID = 3; --  Safe, plan reuse

Intermediate

Q6. What is TRY-CATCH in stored procedures?

CREATE PROCEDURE SafeInsertEmployee
    @Name VARCHAR(100),
    @DeptID INT
AS
BEGIN
    BEGIN TRY
        BEGIN TRANSACTION;

        INSERT INTO Employees(Name, DeptID) VALUES (@Name, @DeptID);

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION;

        -- Capture error details
        SELECT
            ERROR_NUMBER() AS ErrorNumber,
            ERROR_MESSAGE() AS ErrorMessage,
            ERROR_LINE() AS ErrorLine;
    END CATCH
END;

Q7. What is a Nested Stored Procedure? What is @@NESTLEVEL?

Stored procedures can call other stored procedures. Nesting is tracked by @@NESTLEVEL (max 32 levels in SQL Server).

CREATE PROCEDURE OuterProc AS
BEGIN
    PRINT @@NESTLEVEL; -- Prints 1
    EXEC InnerProc;
END;

CREATE PROCEDURE InnerProc AS
BEGIN
    PRINT @@NESTLEVEL; -- Prints 2
END;

Q8. How do you handle transactions spanning multiple stored procedures?

-- Outer SP begins transaction
CREATE PROCEDURE OuterSP AS
BEGIN
    BEGIN TRANSACTION;
    BEGIN TRY
        EXEC InnerSP1;
        EXEC InnerSP2;
        COMMIT;
    END TRY
    BEGIN CATCH
        ROLLBACK;
    END CATCH
END;

If InnerSP issues a ROLLBACK, it rolls back the entire outer transaction — be careful with nested ROLLBACK.

Q9. What is RETURN in a stored procedure vs OUTPUT parameter?

-- RETURN sends an integer status code (convention: 0 = success, negative = error)
CREATE PROCEDURE CheckEmployee @EmpID INT AS
BEGIN
    IF NOT EXISTS (SELECT 1 FROM Employees WHERE EmpID = @EmpID)
        RETURN -1; -- Not found
    RETURN 0;  -- Success
END;

DECLARE @Status INT;
EXEC @Status = CheckEmployee @EmpID = 101;
IF @Status = -1 PRINT 'Employee not found';

Q10. What is WITH RECOMPILE in a stored procedure?

-- Recompile every execution (fresh plan, no caching)
CREATE PROCEDURE GetOrders @StatusID INT
WITH RECOMPILE
AS
BEGIN
    SELECT * FROM Orders WHERE StatusID = @StatusID;
END;

-- Or recompile just once
EXEC GetOrders @StatusID = 2 WITH RECOMPILE;

Use when data distribution is highly skewed and parameter sniffing causes bad plans.

Q11. What is the difference between ALTER PROCEDURE and DROP + CREATE?

-- ALTER: Preserves permissions, dependencies, and existing extended properties
ALTER PROCEDURE GetEmployees AS BEGIN ... END;

-- DROP + CREATE: Loses all permissions; must re-grant
DROP PROCEDURE GetEmployees;
CREATE PROCEDURE GetEmployees AS BEGIN ... END;

Best practice: Always use ALTER in production deployments.

Q12. Commonly ignored — What is SET NOCOUNT ON and why use it?

CREATE PROCEDURE GetEmployees AS
BEGIN
    SET NOCOUNT ON; -- Suppresses "X rows affected" messages
    SELECT * FROM Employees;
END;

Without SET NOCOUNT ON:

  • Every DML sends a DONE_IN_PROC message to the client
  • In loops or batch operations → significant network overhead
  • Some ORMs/drivers may misinterpret these messages as errors

Q13. Commonly ignored — What is deferred name resolution in Stored Procedures?

SQL Server does not validate referenced object names at creation time — only at execution time. A SP can be created referencing a table that doesn’t exist yet.

-- This creates successfully even if FutureTable doesn't exist!
CREATE PROCEDURE UseNonExistentTable AS
BEGIN
    SELECT * FROM FutureTable; -- Error only at runtime
END;

This is different from Views and Functions which do validate at creation.

Advanced

Q14. How do you return multiple result sets from a stored procedure?

CREATE PROCEDURE GetDashboardData AS
BEGIN
    SET NOCOUNT ON;
    SELECT COUNT(*) AS TotalEmployees FROM Employees;       -- Result set 1
    SELECT DeptName, COUNT(*) FROM Employees                -- Result set 2
        JOIN Departments ON Employees.DeptID = Departments.DeptID
        GROUP BY DeptName;
END;

-- reader.Read(); // First result set
-- reader.NextResult(); // Move to second result set

Q15. What is Dynamic SQL in Stored Procedures? When is it necessary?

CREATE PROCEDURE SearchEmployees
    @ColumnName NVARCHAR(50),
    @SearchValue NVARCHAR(100)
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @SQL NVARCHAR(1000);

    -- Whitelist column names to prevent injection
    IF @ColumnName NOT IN ('Name', 'Email', 'Phone')
        THROW 50001, 'Invalid column name', 1;

    SET @SQL = N'SELECT * FROM Employees WHERE ' + QUOTENAME(@ColumnName) +
               N' = @Val';

    EXEC sp_executesql @SQL, N'@Val NVARCHAR(100)', @Val = @SearchValue;
END;

Use QUOTENAME() to safely quote identifiers. Use sp_executesql with parameters to prevent SQL injection.

Q16. Commonly ignored — What is XACT_ABORT in stored procedures?

CREATE PROCEDURE SafeTransfer AS
BEGIN
    SET XACT_ABORT ON; -- Automatically ROLLBACK on any runtime error
    BEGIN TRANSACTION;

    UPDATE Accounts SET Balance = Balance - 1000 WHERE AccountID = 1;
    UPDATE Accounts SET Balance = Balance + 1000 WHERE AccountID = 2;

    COMMIT;
END;

Without SET XACT_ABORT ON, some errors (like constraint violations) don’t automatically rollback the transaction — leaving it in an open state.

Q17. Commonly ignored — What is @@ROWCOUNT and @@ERROR?

CREATE PROCEDURE UpdateSalary @EmpID INT, @NewSalary DECIMAL(10,2) AS
BEGIN
    UPDATE Employees SET Salary = @NewSalary WHERE EmpID = @EmpID;

    IF @@ROWCOUNT = 0
        PRINT 'No employee found with that ID';

    IF @@ERROR <> 0
        PRINT 'An error occurred';
END;

@@ERROR and @@ROWCOUNT reset after every statement — capture them immediately after the statement.

Q18. Commonly ignored — Stored Procedure vs Table-Valued Function for reuse in queries?

-- SP cannot be used in FROM clause 
SELECT * FROM EXEC GetEmployees(); -- Invalid!

-- Table-Valued Function can be 
CREATE FUNCTION GetActiveEmployees()
RETURNS TABLE AS
RETURN (SELECT * FROM Employees WHERE IsActive = 1);

SELECT * FROM GetActiveEmployees() WHERE DeptID = 3;

When you need to use the result set as a subquery or JOIN source, use a TVF, not a SP.

-- 1. Add PRINT statements

RAISERROR('Debug: DeptID = %d', 0, 1, @DeptID) WITH NOWAIT;

SELECT * FROM sys.dm_exec_procedure_stats

Quick Reference Cheat Sheet

Index Decision Guide

Query has WHERE on column?  → Create index on that column
Query selects extra columns? → Use INCLUDE (covering index)
Multiple WHERE conditions?  → Composite index (order: equality → range)
Only specific rows queried? → Filtered index
Text search needed?         → Full-text index

DELETE / TRUNCATE / DROP Quick Pick

Remove specific rows         → DELETE with WHERE
Remove all rows, keep table  → TRUNCATE
Remove table entirely        → DROP TABLE
Need triggers to fire        → DELETE (TRUNCATE won't fire them)
Need FK-safe removal         → DELETE (TRUNCATE fails with FK references)

Optimization Checklist

☐ Use SELECT <columns> not SELECT *
☐ Ensure predicates are SARGable (no function on column in WHERE)
☐ Match data types to avoid implicit conversion
☐ Use EXISTS over IN for subqueries (especially with NULLs)
☐ Check execution plan for Key Lookups → add INCLUDE columns
☐ Update statistics on large tables
☐ Use sp_executesql for dynamic SQL
☐ Batch large deletes/updates
☐ Replace OR with UNION ALL for index-friendly queries

Stored Procedure Best Practices

☐ Always use SET NOCOUNT ON
☐ Always use SET XACT_ABORT ON with transactions
☐ Use TRY-CATCH for error handling
☐ Capture @@ROWCOUNT and @@ERROR immediately
☐ Use ALTER PROCEDURE (not DROP + CREATE) in production
☐ Parameterize dynamic SQL with sp_executesql
☐ Whitelist dynamic column/table names with QUOTENAME()
