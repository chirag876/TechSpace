1. CTE vs Temp Table

The Setup

You are writing a query. The logic is complex. You need an intermediate result that feeds into a larger query. You have three tools: a CTE, a Temp Table, or a Table Variable. Choosing the wrong one makes your query unreadable, slow, or both.

CTE — Common Table Expression

A CTE is a named subquery defined at the top of your main query using the WITH keyword. It has no physical existence — it is not stored anywhere. It is a way to give a name to a subquery and reference it once (or multiple times) in the query that follows.

Think of it as giving a nickname to a complex expression so you can refer to it cleanly.

-- Syntax
WITH CTEName AS
(
    -- This is just a SELECT statement
    SELECT column1, column2
    FROM SomeTable
    WHERE SomeCondition = 1
)
-- The CTE is used here, immediately after its definition
SELECT * FROM CTEName WHERE column1 > 100;

Real example — finding customers who spent above average:

WITH CustomerSpend AS
(
    SELECT
        CustomerId,
        SUM(TotalAmount) AS TotalSpend
    FROM Orders
    WHERE Status = 'Completed'
    GROUP BY CustomerId
),
AverageSpend AS
(
    SELECT AVG(TotalSpend) AS AvgSpend
    FROM CustomerSpend
)
SELECT
    c.Name,
    cs.TotalSpend,
    av.AvgSpend,
    cs.TotalSpend - av.AvgSpend AS AboveAvgBy
FROM CustomerSpend cs
JOIN Customers c ON cs.CustomerId = c.CustomerId
CROSS JOIN AverageSpend av
WHERE cs.TotalSpend > av.AvgSpend
ORDER BY cs.TotalSpend DESC;

Notice: multiple CTEs are chained with commas. Each one can reference the ones defined before it. The main query uses all of them. No temp tables created, no cleanup needed.

Recursive CTE — Hierarchical Data

This is where CTEs shine uniquely. No temp table or subquery can naturally replace a recursive CTE. Use it for hierarchical data: organizational charts, category trees, bill of materials, file systems.

-- Employee hierarchy — who reports to whom, all levels deep
WITH EmployeeHierarchy AS
(
    -- Anchor member: the starting point (top of the hierarchy)
    SELECT
        EmployeeId,
        Name,
        ManagerId,
        0 AS Level,
        CAST(Name AS NVARCHAR(MAX)) AS HierarchyPath
    FROM Employees
    WHERE ManagerId IS NULL   -- The CEO — no manager

    UNION ALL

    -- Recursive member: joins back to the CTE itself
    SELECT
        e.EmployeeId,
        e.Name,
        e.ManagerId,
        eh.Level + 1,
        CAST(eh.HierarchyPath + ' > ' + e.Name AS NVARCHAR(MAX))
    FROM Employees e
    JOIN EmployeeHierarchy eh ON e.ManagerId = eh.EmployeeId
    -- SQL Server stops recursion when no more rows match
    -- Default max recursion: 100 levels (change with OPTION (MAXRECURSION n))
)
SELECT
    REPLICATE('    ', Level) + Name AS OrgChart,  -- Indentation shows level
    Level,
    HierarchyPath
FROM EmployeeHierarchy
ORDER BY HierarchyPath;

-- Output:
-- CEO
--     VP of Engineering
--         Senior Engineer
--             Junior Engineer
--     VP of Sales
--         Sales Manager

-- Generate a date series (no Calendar table needed)
WITH DateSeries AS
(
    SELECT CAST('2024-01-01' AS DATE) AS DateValue

    UNION ALL

    SELECT DATEADD(DAY, 1, DateValue)
    FROM DateSeries
    WHERE DateValue < '2024-12-31'
)
SELECT DateValue, DATENAME(WEEKDAY, DateValue) AS DayName
FROM DateSeries
OPTION (MAXRECURSION 400); -- Override the 100-level default

Temp Table — Physical Intermediate Storage

A temp table is a real table stored in tempdb. It has physical pages, can have indexes, and SQL Server builds statistics on it — allowing accurate execution plans for queries that reference it.

-- Create explicitly
CREATE TABLE #CustomerOrders
(
    CustomerId   INT           NOT NULL,
    CustomerName NVARCHAR(200) NOT NULL,
    OrderCount   INT           NOT NULL,
    TotalSpend   DECIMAL(18,2) NOT NULL
);

-- Insert data
INSERT INTO #CustomerOrders (CustomerId, CustomerName, OrderCount, TotalSpend)
SELECT
    c.CustomerId,
    c.Name,
    COUNT(o.OrderId),
    SUM(o.TotalAmount)
FROM Customers c
JOIN Orders o ON c.CustomerId = o.CustomerId
WHERE o.OrderDate >= '2024-01-01'
GROUP BY c.CustomerId, c.Name;

-- Add an index to make subsequent queries fast
CREATE INDEX IX_Temp_TotalSpend ON #CustomerOrders (TotalSpend DESC);

-- Use it multiple times in the same session
SELECT * FROM #CustomerOrders WHERE TotalSpend > 10000;
SELECT AVG(TotalSpend) FROM #CustomerOrders;
SELECT TOP 10 * FROM #CustomerOrders ORDER BY TotalSpend DESC;

-- Temp tables are dropped automatically when the session ends
-- Drop manually for clarity and to release tempdb space early
DROP TABLE IF EXISTS #CustomerOrders;

SELECT INTO — the quick version:

-- Creates and populates a temp table in one statement
-- SQL Server infers the column names and types from the SELECT
SELECT
    c.CustomerId,
    c.Name,
    COUNT(o.OrderId)    AS OrderCount,
    SUM(o.TotalAmount)  AS TotalSpend
INTO #CustomerOrders    -- Creates the table automatically
FROM Customers c
JOIN Orders o ON c.CustomerId = o.CustomerId
GROUP BY c.CustomerId, c.Name;

-- Downside of SELECT INTO: cannot add constraints or specify NOT NULL before inserting
-- Use explicit CREATE TABLE when you need control over the schema

Table Variable — The Lightweight Option

A table variable lives in memory (and spills to tempdb if it grows large). It is scoped to the batch or stored procedure in which it is declared. It cannot have indexes beyond a primary key. SQL Server always estimates 1 row regardless of actual data — which can produce terrible execution plans for large datasets.

DECLARE @TopCustomers TABLE
(
    CustomerId  INT          PRIMARY KEY,
    TotalSpend  DECIMAL(18,2)
);

INSERT INTO @TopCustomers
SELECT TOP 100 CustomerId, SUM(TotalAmount)
FROM Orders
GROUP BY CustomerId
ORDER BY SUM(TotalAmount) DESC;

-- SQL Server assumes this table has 1 row when building the execution plan
-- For 100 rows this is fine; for 100,000 rows, the plan will be wrong
SELECT c.Name, tc.TotalSpend
FROM @TopCustomers tc
JOIN Customers c ON tc.CustomerId = c.CustomerId;

When to Use Which

The decision comes down to three questions: How complex is the query? How large is the data? Do you need to use the result more than once?

CTE — use when:
    The data is used only once (in the immediately following query)
    You need readability — breaking complex logic into named steps
    You need recursion (only CTEs can do this cleanly)
    The intermediate result is not huge
    You do not need multiple separate queries against the intermediate result

Temp Table — use when:
    The intermediate result is large (thousands of rows or more)
    You need to query the intermediate result multiple times
    You need indexes on the intermediate result for performance
    You are inside a stored procedure and need to pass data between steps
    You want SQL Server to build accurate statistics for the optimizer
    You need to INSERT, UPDATE, or DELETE from the intermediate result

Table Variable — use when:
    The dataset is small (a few hundred rows at most)
    You are inside a stored procedure with a short lifecycle
    You want automatic cleanup without DROP TABLE
    Transaction rollback should NOT undo the data (table variables survive ROLLBACK)

Side-by-Side Comparison

Feature CTE Temp Table Table Variable
Physical storage None tempdb Memory / tempdb
Can be indexed No Yes Primary key only
Statistics built No Yes No (always 1 row)
Scope Single statement Session Batch / procedure
Recursive Yes No No
Survives ROLLBACK N/A No Yes
Multiple queries No (use once) Yes Yes
Best for Readability, recursion Large intermediate data Small datasets
Cleanup needed No Yes (or end of session) No (auto)

A Complete Example — All Three Together

-- Step 1: Heavy aggregation stored in a temp table (large data, used multiple times)
SELECT
    ProductId,
    SUM(Quantity)   AS TotalSold,
    SUM(Revenue)    AS TotalRevenue
INTO #ProductSales
FROM SalesLineItems
WHERE SaleDate >= '2024-01-01'
GROUP BY ProductId;

CREATE INDEX IX_PS_Revenue ON #ProductSales (TotalRevenue DESC);

-- Step 2: CTE for readability — rank products within each category
WITH RankedProducts AS
(
    SELECT
        p.ProductId,
        p.CategoryId,
        p.Name,
        ps.TotalRevenue,
        RANK() OVER (PARTITION BY p.CategoryId ORDER BY ps.TotalRevenue DESC) AS RankInCategory
    FROM #ProductSales ps
    JOIN Products p ON ps.ProductId = p.ProductId
)
-- Step 3: Final result — top 3 products per category
SELECT CategoryId, Name, TotalRevenue, RankInCategory
FROM RankedProducts
WHERE RankInCategory <= 3
ORDER BY CategoryId, RankInCategory;

-- Step 4: Second use of the temp table (impossible with a CTE)
SELECT AVG(TotalRevenue) AS AvgRevenuePerProduct FROM #ProductSales;

DROP TABLE IF EXISTS #ProductSales;

2. JOINs

What Is a JOIN?

Tables in a relational database are separate for a reason — normalisation avoids duplicating data. Orders do not store the customer name; they store a CustomerId. To get the customer name alongside the order, you JOIN the two tables.

A JOIN combines rows from two or more tables based on a related column — the join condition. The result is a new virtual table containing columns from both sources.

Sample Tables Used Throughout This Section

-- Customers table
CustomerId | Name          | Country
-----------|---------------|--------
1          | Alice         | India
2          | Bob           | USA
3          | Charlie       | India
4          | Diana         | UK

-- Orders table
OrderId | CustomerId | TotalAmount | Status
--------|------------|-------------|----------
101     | 1          | 500.00      | Completed
102     | 1          | 300.00      | Pending
103     | 2          | 150.00      | Completed
104     | 5          | 900.00      | Completed   <- CustomerId 5 does not exist in Customers

INNER JOIN — Only the Matches

Returns rows that have a match in BOTH tables. If a row in the left table has no match in the right table (or vice versa), it is excluded.

SELECT
    c.Name,
    o.OrderId,
    o.TotalAmount
FROM Customers c
INNER JOIN Orders o ON c.CustomerId = o.CustomerId;

-- Result:
-- Alice   | 101 | 500.00
-- Alice   | 102 | 300.00
-- Bob     | 103 | 150.00
-- Charlie is excluded (no orders)
-- Diana   is excluded (no orders)
-- Order 104 is excluded (CustomerId 5 does not exist in Customers)

The word INNER is optional. JOIN alone means INNER JOIN.

LEFT JOIN — All Left Rows, Matched Right Rows

Returns all rows from the left table. For rows in the left table that have no match in the right table, the right table columns are NULL.

SELECT
    c.Name,
    o.OrderId,
    o.TotalAmount
FROM Customers c                            -- LEFT table
LEFT JOIN Orders o ON c.CustomerId = o.CustomerId;  -- RIGHT table

-- Result:
-- Alice   | 101  | 500.00
-- Alice   | 102  | 300.00
-- Bob     | 103  | 150.00
-- Charlie | NULL | NULL    <- No orders, but Charlie is still in the result
-- Diana   | NULL | NULL    <- No orders, but Diana is still in the result
-- Order 104 is excluded (no matching Customer)

-- Finding customers with NO orders (the classic LEFT JOIN + IS NULL pattern)
SELECT c.Name
FROM Customers c
LEFT JOIN Orders o ON c.CustomerId = o.CustomerId
WHERE o.OrderId IS NULL;
-- Result: Charlie, Diana

LEFT OUTER JOIN and LEFT JOIN are identical. OUTER is optional.

RIGHT JOIN — All Right Rows, Matched Left Rows

Returns all rows from the right table. For rows in the right table that have no match in the left table, the left table columns are NULL.

SELECT
    c.Name,
    o.OrderId,
    o.TotalAmount
FROM Customers c
RIGHT JOIN Orders o ON c.CustomerId = o.CustomerId;

-- Result:
-- Alice | 101 | 500.00
-- Alice | 102 | 300.00
-- Bob   | 103 | 150.00
-- NULL  | 104 | 900.00   <- Order 104 has no matching customer, still appears

-- In practice, RIGHT JOIN is almost never used.
-- Every RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the table order.
-- Most developers always LEFT JOIN for consistency.
-- Rewritten:
SELECT c.Name, o.OrderId, o.TotalAmount
FROM Orders o
LEFT JOIN Customers c ON o.CustomerId = c.CustomerId;
-- Same result, more readable convention

FULL OUTER JOIN — Everything from Both Sides

Returns all rows from both tables. Where there is a match, columns from both tables are populated. Where there is no match, the missing side is NULL.

SELECT
    c.Name,
    o.OrderId,
    o.TotalAmount
FROM Customers c
FULL OUTER JOIN Orders o ON c.CustomerId = o.CustomerId;

-- Result:
-- Alice   | 101  | 500.00
-- Alice   | 102  | 300.00
-- Bob     | 103  | 150.00
-- Charlie | NULL | NULL    <- Customer with no order
-- Diana   | NULL | NULL    <- Customer with no order
-- NULL    | 104  | 900.00  <- Order with no customer

-- Finding rows that exist in one table but NOT the other (the orphan finder)
SELECT c.Name, o.OrderId
FROM Customers c
FULL OUTER JOIN Orders o ON c.CustomerId = o.CustomerId
WHERE c.CustomerId IS NULL OR o.OrderId IS NULL;
-- Result:
-- Charlie | NULL   <- No orders
-- Diana   | NULL   <- No orders
-- NULL    | 104    <- No customer

CROSS JOIN — Every Combination

Returns the Cartesian product of both tables — every row from the left table paired with every row from the right table. No join condition.

SELECT c.Name, s.Size
FROM Customers c
CROSS JOIN Sizes s;

-- If Customers has 4 rows and Sizes has 3 rows (S, M, L):
-- Result has 4 x 3 = 12 rows
-- Alice - S
-- Alice - M
-- Alice - L
-- Bob   - S
-- Bob   - M
-- ... and so on

-- Useful for:
-- Generating all combinations (menu items x options, employees x shifts)
-- Pairing a lookup table with every row (like a constant or scalar value)
-- Stress testing with generated data

-- CROSS JOIN with a single-row CTE (clean way to reference a constant)
WITH Config AS (SELECT 0.18 AS TaxRate)
SELECT
    o.OrderId,
    o.TotalAmount,
    o.TotalAmount * c.TaxRate AS TaxAmount
FROM Orders o
CROSS JOIN Config c;

SELF JOIN — A Table Joined to Itself

A self join joins a table to itself. The same table appears twice under different aliases. This is how you query hierarchical data stored in a single table.

-- Employees table: EmployeeId, Name, ManagerId (ManagerId references EmployeeId)
-- Find each employee and their manager's name

SELECT
    e.Name        AS Employee,
    m.Name        AS Manager
FROM Employees e
LEFT JOIN Employees m ON e.ManagerId = m.EmployeeId;
-- LEFT JOIN so the CEO (NULL ManagerId) still appears with NULL for Manager

-- Result:
-- CEO       | NULL
-- VP Eng    | CEO
-- Sr Eng    | VP Eng
-- Jr Eng    | Sr Eng
-- VP Sales  | CEO

Multiple JOINs — Chaining Tables Together

-- Order details with customer name, product name, and category
SELECT
    c.Name              AS CustomerName,
    o.OrderId,
    o.OrderDate,
    p.Name              AS ProductName,
    cat.Name            AS CategoryName,
    oi.Quantity,
    oi.UnitPrice,
    oi.Quantity * oi.UnitPrice AS LineTotal
FROM Orders o
JOIN Customers   c   ON o.CustomerId    = c.CustomerId
JOIN OrderItems  oi  ON o.OrderId       = oi.OrderId
JOIN Products    p   ON oi.ProductId    = p.ProductId
JOIN Categories  cat ON p.CategoryId    = cat.CategoryId
WHERE o.OrderDate >= '2024-01-01'
  AND c.Country = 'India'
ORDER BY o.OrderDate DESC;

SQL Server processes joins left to right, but the Query Optimizer may reorder them for performance. The logical meaning is always: start with the FROM table, attach each joined table in sequence.

JOIN on Multiple Conditions

-- Join on more than one column when a single column is not unique enough
SELECT *
FROM OrderItems oi
JOIN PriceHistory ph
    ON  oi.ProductId = ph.ProductId
    AND oi.OrderDate BETWEEN ph.EffectiveFrom AND ph.EffectiveTo;
-- Finds the price that was active when the order was placed

-- Join with an inequality condition
SELECT
    a.EmployeeId,
    a.Salary,
    b.EmployeeId AS HigherPaidEmployee,
    b.Salary     AS HigherSalary
FROM Employees a
JOIN Employees b ON a.DepartmentId = b.DepartmentId
               AND a.Salary < b.Salary;
-- Finds all pairs within a department where one earns more than the other

JOIN Performance Rules

-- Rule 1: Always join on indexed columns
-- The join column on BOTH tables should have an index
-- If CustomerId is the PK of Customers (clustered index) and
-- a nonclustered index on Orders.CustomerId exists, the join is fast

-- Rule 2: Data types must match
-- Joining INT to BIGINT or INT to VARCHAR causes implicit conversion
-- Implicit conversion disables index usage on the converted column

-- Rule 3: Filter early
-- Put WHERE conditions that significantly reduce rows before the join
-- SQL Server's optimizer usually handles this, but explicit filtering in a subquery helps
-- for very complex queries where the optimizer makes bad estimates

-- Rule 4: Avoid functions on join columns
-- BAD
JOIN Customers c ON LOWER(o.Email) = LOWER(c.Email)  -- Full scan, no index

-- GOOD
JOIN Customers c ON o.Email = c.Email  -- Index seek on Email
-- Enforce consistent casing at insert time or use a case-insensitive collation

-- Rule 5: Be careful with OR conditions in joins
-- An OR in a JOIN condition prevents efficient index usage
-- BAD
JOIN Employees m ON e.ManagerId = m.EmployeeId OR e.AlternateManagerId = m.EmployeeId

-- GOOD — split into two joins, combine with UNION or COALESCE

Visual Summary of JOINs

Table A: [1] [2] [3] [4]
Table B: [3] [4] [5] [6]

INNER JOIN:         [3] [4]              -- Only where both match

LEFT JOIN:   [1] [2] [3] [4]            -- All of A, matched B (NULLs for 1,2)
              NULL NULL [3] [4]

RIGHT JOIN:             [3] [4] [5] [6]  -- All of B, matched A (NULLs for 5,6)

FULL OUTER:  [1] [2] [3] [4] [5] [6]   -- Everything from both sides

CROSS JOIN:  [1x3][1x4][1x5][1x6]
             [2x3][2x4][2x5][2x6]      -- Every combination
             [3x3][3x4][3x5][3x6]
             [4x3][4x4][4x5][4x6]

3. GROUP BY and HAVING

What GROUP BY Does

GROUP BY collapses multiple rows into one row per unique combination of the grouped columns. It is how you go from row-level data to summary data.

Think of it like sorting your data into buckets. All orders from the same customer go into the same bucket. All products from the same category go into the same bucket. Then you run a calculation on each bucket — count, sum, average, min, max.

-- Without GROUP BY: one row per order
SELECT CustomerId, TotalAmount FROM Orders;
-- 10,000 rows

-- With GROUP BY: one row per customer
SELECT CustomerId, SUM(TotalAmount) AS TotalSpend
FROM Orders
GROUP BY CustomerId;
-- As many rows as there are distinct customers

-- Multiple columns: one row per (CustomerId, Status) combination
SELECT CustomerId, Status, COUNT(*) AS OrderCount, SUM(TotalAmount) AS TotalSpend
FROM Orders
GROUP BY CustomerId, Status;

The Golden Rule of GROUP BY

Every column in the SELECT list must either be in the GROUP BY clause or be inside an aggregate function.

-- WRONG — Name is not in GROUP BY and not aggregated
SELECT CustomerId, Name, SUM(TotalAmount)
FROM Orders
GROUP BY CustomerId;
-- Error: Column 'Orders.Name' is invalid in the select list because it is not
-- contained in either an aggregate function or the GROUP BY clause.

-- CORRECT option 1: Add Name to GROUP BY
SELECT CustomerId, Name, SUM(TotalAmount)
FROM Orders
GROUP BY CustomerId, Name;

-- CORRECT option 2: Aggregate Name
SELECT CustomerId, MAX(Name) AS Name, SUM(TotalAmount)
FROM Orders
GROUP BY CustomerId;

-- CORRECT option 3: Join to get Name after grouping
SELECT o.CustomerId, c.Name, o.TotalSpend
FROM (
    SELECT CustomerId, SUM(TotalAmount) AS TotalSpend
    FROM Orders
    GROUP BY CustomerId
) o
JOIN Customers c ON o.CustomerId = c.CustomerId;

Aggregate Functions

SELECT
    CustomerId,
    COUNT(*)                    AS TotalOrders,         -- Counts every row in the group
    COUNT(DiscountCode)         AS OrdersWithDiscount,  -- Counts non-NULL values only
    COUNT(DISTINCT ProductId)   AS UniqueProducts,      -- Counts distinct non-NULL values
    SUM(TotalAmount)            AS TotalSpend,
    AVG(TotalAmount)            AS AvgOrderValue,
    MIN(TotalAmount)            AS SmallestOrder,
    MAX(TotalAmount)            AS LargestOrder,
    MIN(OrderDate)              AS FirstOrderDate,
    MAX(OrderDate)              AS LastOrderDate,
    STDEV(TotalAmount)          AS StdDeviation,
    VAR(TotalAmount)            AS Variance
FROM Orders
GROUP BY CustomerId;

COUNT(*) vs COUNT(column):

-- COUNT(*) counts rows — including rows where the column is NULL
-- COUNT(column) counts non-NULL values in that column — NULLs are skipped

-- Example: 5 orders, 3 have a DiscountCode, 2 have NULL
SELECT
    COUNT(*)            AS TotalOrders,      -- 5
    COUNT(DiscountCode) AS OrdersWithDiscount -- 3 (NULLs not counted)
FROM Orders;

-- This is often used to count how many rows have a value
SELECT ProductId, COUNT(ReviewText) AS ReviewsWithText
FROM Reviews
GROUP BY ProductId;

ORDER OF EXECUTION — This Is Critical

SQL processes clauses in this order, which is NOT the order you write them:

1. FROM       -- which table(s)
2. JOIN       -- combine tables
3. WHERE      -- filter rows BEFORE grouping
4. GROUP BY   -- collapse into groups
5. HAVING     -- filter groups AFTER grouping
6. SELECT     -- compute output columns
7. DISTINCT   -- remove duplicate output rows
8. ORDER BY   -- sort the final result
9. TOP/OFFSET -- limit the result

Writing order:  SELECT ... FROM ... JOIN ... WHERE ... GROUP BY ... HAVING ... ORDER BY
Execution order: FROM -> JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY

This order explains why you cannot use a column alias defined in SELECT inside a WHERE clause — WHERE executes before SELECT. And why you use HAVING for aggregate conditions but WHERE for row-level conditions.

WHERE vs HAVING — The Most Common Confusion

WHERE  = filter rows BEFORE grouping  (works on individual rows, raw columns)
HAVING = filter groups AFTER grouping (works on groups, can use aggregate functions)

-- WHERE filters rows before they enter the group
-- Only orders from 2024 are included in the groups
SELECT CustomerId, SUM(TotalAmount) AS TotalSpend
FROM Orders
WHERE OrderDate >= '2024-01-01'    -- Applied before grouping (fast — can use index)
GROUP BY CustomerId;

-- HAVING filters groups after grouping
-- Only customers whose total spend exceeds 10,000 are in the result
SELECT CustomerId, SUM(TotalAmount) AS TotalSpend
FROM Orders
GROUP BY CustomerId
HAVING SUM(TotalAmount) > 10000;   -- Applied after grouping (must compute SUM first)

-- BOTH together — most common pattern
SELECT
    CustomerId,
    COUNT(*)         AS OrderCount,
    SUM(TotalAmount) AS TotalSpend
FROM Orders
WHERE OrderDate >= '2024-01-01'    -- Row filter: only 2024 orders
  AND Status = 'Completed'         -- Row filter: only completed orders
GROUP BY CustomerId
HAVING COUNT(*) >= 3               -- Group filter: only customers with 3+ orders
   AND SUM(TotalAmount) > 5000     -- Group filter: only customers who spent > 5000
ORDER BY TotalSpend DESC;

Why not use HAVING for everything?

-- WRONG approach: using HAVING to filter a non-aggregate condition
-- Works but is inefficient — all rows enter grouping, then half are discarded
SELECT CustomerId, SUM(TotalAmount)
FROM Orders
GROUP BY CustomerId
HAVING CustomerId > 100;  -- Should be in WHERE

-- CORRECT: push non-aggregate filters to WHERE
-- Fewer rows enter the GROUP BY operation
SELECT CustomerId, SUM(TotalAmount)
FROM Orders
WHERE CustomerId > 100    -- Filtered before grouping (can use index on CustomerId)
GROUP BY CustomerId;

ROLLUP — Subtotals and Grand Totals

ROLLUP adds summary rows for each level of grouping and a grand total at the end.

SELECT
    Country,
    City,
    SUM(TotalAmount) AS TotalSales
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
GROUP BY ROLLUP(Country, City);

-- Result:
-- India   | Mumbai   | 15000    <- City-level total
-- India   | Delhi    | 22000    <- City-level total
-- India   | NULL     | 37000    <- Country-level subtotal (ROLLUP added this)
-- USA     | New York | 8000     <- City-level total
-- USA     | NULL     | 8000     <- Country-level subtotal
-- NULL    | NULL     | 45000    <- Grand total (ROLLUP added this)

-- Distinguish ROLLUP NULLs from actual NULL values in data
SELECT
    ISNULL(Country, 'GRAND TOTAL')  AS Country,
    ISNULL(City, 'SUBTOTAL')        AS City,
    SUM(TotalAmount)                AS TotalSales
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
GROUP BY ROLLUP(Country, City);

GROUPING SETS — Custom Grouping Combinations

-- Generate multiple grouping levels in one query
SELECT
    Country,
    Category,
    SUM(TotalAmount) AS TotalSales
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
JOIN Products p ON o.ProductId = p.ProductId
GROUP BY GROUPING SETS
(
    (Country, Category),  -- Total per Country+Category combination
    (Country),            -- Total per Country
    (Category),           -- Total per Category
    ()                    -- Grand total
);

Window Functions with GROUP BY

Window functions (OVER) do not collapse rows the way GROUP BY does. They compute a value for each row while still showing all rows. This is a powerful combination.

-- Show each order AND the customer's total spend side by side
-- Without GROUP BY collapsing rows
SELECT
    CustomerId,
    OrderId,
    TotalAmount,
    SUM(TotalAmount)    OVER (PARTITION BY CustomerId) AS CustomerTotalSpend,
    COUNT(*)            OVER (PARTITION BY CustomerId) AS CustomerOrderCount,
    AVG(TotalAmount)    OVER (PARTITION BY CustomerId) AS CustomerAvgOrder,
    TotalAmount * 1.0 /
        SUM(TotalAmount) OVER (PARTITION BY CustomerId) AS PctOfCustomerTotal
FROM Orders
ORDER BY CustomerId, OrderId;

-- Running total (cumulative sum)
SELECT
    OrderId,
    OrderDate,
    TotalAmount,
    SUM(TotalAmount) OVER (ORDER BY OrderDate ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
        AS RunningTotal
FROM Orders
ORDER BY OrderDate;

-- Ranking within groups
SELECT
    CustomerId,
    OrderId,
    TotalAmount,
    ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY TotalAmount DESC) AS RowNum,
    RANK()       OVER (PARTITION BY CustomerId ORDER BY TotalAmount DESC) AS Rank,
    DENSE_RANK() OVER (PARTITION BY CustomerId ORDER BY TotalAmount DESC) AS DenseRank
FROM Orders;

-- Get the top 1 order per customer using ROW_NUMBER()
WITH RankedOrders AS
(
    SELECT
        CustomerId,
        OrderId,
        TotalAmount,
        ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY TotalAmount DESC) AS RowNum
    FROM Orders
)
SELECT CustomerId, OrderId, TotalAmount
FROM RankedOrders
WHERE RowNum = 1;  -- The largest order per customer

ROW_NUMBER vs RANK vs DENSE_RANK:

Values: 100, 90, 90, 80

ROW_NUMBER:  1,  2,  3,  4   -- Always unique, no gaps, no ties
RANK:        1,  2,  2,  4   -- Ties share rank, gap after (skips 3)
DENSE_RANK:  1,  2,  2,  3   -- Ties share rank, NO gap after

4. Functions

Categories of Functions in SQL Server

1. Scalar Functions         -- Return a single value
2. Aggregate Functions      -- Operate on a set of rows, return one value
3. Table-Valued Functions   -- Return a table (inline or multi-statement)
4. System Functions         -- Built-in: GETDATE(), NEWID(), ISNULL(), etc.
5. Window Functions         -- Operate over a partition of rows (OVER clause)

String Functions

-- Length and case
SELECT LEN('Hello World');            -- 11 (excludes trailing spaces)

SELECT REPLACE('Hello World', 'World', 'SQL'); -- 'Hello SQL'

FROM Products;

Conversion and NULL Handling Functions

-- Type conversion
SELECT CAST('42' AS INT);               -- 42
SELECT CAST(42.9 AS INT);               -- 42 (truncates, does not round)
SELECT CAST(GETDATE() AS DATE);         -- '2024-05-24' (strips time)
SELECT CONVERT(DECIMAL(10,2), '42.567'); -- 42.57

-- Safe conversion (returns NULL on failure instead of error)
SELECT TRY_CAST('abc' AS INT);           -- NULL (not an error)
SELECT TRY_CAST('42' AS INT);            -- 42
SELECT TRY_CONVERT(INT, 'abc');          -- NULL

-- NULL handling
SELECT ISNULL(NULL, 'default');           -- 'default'
SELECT ISNULL('value', 'default');        -- 'value'
SELECT COALESCE(NULL, NULL, 'third', 'fourth'); -- 'third' (first non-NULL)
SELECT NULLIF(5, 5);                      -- NULL (returns NULL if both args are equal)
SELECT NULLIF(5, 3);                      -- 5   (returns first arg if they differ)

-- NULLIF is great for avoiding divide-by-zero
SELECT TotalRevenue / NULLIF(TotalOrders, 0) AS AvgRevPerOrder
FROM SalesSummary;
-- If TotalOrders is 0, NULLIF returns NULL, so division result is NULL (not an error)

-- COALESCE for fallback values
SELECT
    COALESCE(PreferredName, NickName, FirstName, 'Unknown') AS DisplayName
FROM Users;
-- Uses the first non-NULL value from the list

-- CASE expression (conditional logic)
SELECT
    OrderId,
    TotalAmount,
    CASE Status
        WHEN 'Pending'   THEN 'Awaiting Processing'
        WHEN 'Confirmed' THEN 'In Progress'
        WHEN 'Shipped'   THEN 'On the Way'
        WHEN 'Delivered' THEN 'Completed'
        ELSE 'Unknown Status'
    END AS StatusDescription
FROM Orders;

-- Searched CASE (more flexible — any condition)
SELECT
    ProductId,
    Price,
    CASE
        WHEN Price < 100   THEN 'Budget'
        WHEN Price < 500   THEN 'Mid-Range'
        WHEN Price < 2000  THEN 'Premium'
        ELSE 'Luxury'
    END AS PriceTier
FROM Products;

User-Defined Functions

Scalar Function

Returns one value. Called in a SELECT or WHERE clause.

CREATE FUNCTION dbo.fn_CalculateAge
(
    @DateOfBirth DATE
)
RETURNS INT
AS
BEGIN
    RETURN DATEDIFF(YEAR, @DateOfBirth, GETDATE())
         - CASE
               WHEN MONTH(@DateOfBirth) > MONTH(GETDATE()) THEN 1
               WHEN MONTH(@DateOfBirth) = MONTH(GETDATE())
                AND DAY(@DateOfBirth)   > DAY(GETDATE())   THEN 1
               ELSE 0
           END;
END;
GO

-- Usage
SELECT Name, dbo.fn_CalculateAge(DateOfBirth) AS Age FROM Employees;
SELECT * FROM Employees WHERE dbo.fn_CalculateAge(DateOfBirth) >= 18;

The performance warning with scalar functions:

When you call a scalar UDF in a SELECT or WHERE clause on a large table, it executes once per row. For a million-row table, it runs a million times, each as a separate execution context. This is called the RBAR problem (Row By Agonizing Row).

-- This runs fn_CalculateAge 1,000,000 times — very slow
SELECT Name, dbo.fn_CalculateAge(DateOfBirth) AS Age
FROM Employees; -- 1 million rows

-- Alternative: inline the logic with a CASE expression (set-based, fast)
SELECT
    Name,
    DATEDIFF(YEAR, DateOfBirth, GETDATE())
    - CASE
          WHEN MONTH(DateOfBirth) > MONTH(GETDATE()) THEN 1
          WHEN MONTH(DateOfBirth) = MONTH(GETDATE())
           AND DAY(DateOfBirth)   > DAY(GETDATE())   THEN 1
          ELSE 0
      END AS Age
FROM Employees;
-- This runs as one set-based operation — dramatically faster

SQL Server 2019 introduced scalar UDF inlining — the optimizer can automatically inline simple scalar UDFs into the query plan, removing the per-row execution overhead. But do not rely on it for complex functions.

Inline Table-Valued Function (iTVF)

Returns a table. Defined as a single RETURN statement with no BEGIN...END. The optimizer can look inside an iTVF and merge it into the calling query’s execution plan — making it as fast as writing the query directly.

CREATE FUNCTION dbo.fn_GetCustomerOrders
(
    @CustomerId INT,
    @StartDate  DATE = NULL
)
RETURNS TABLE  -- No AS BEGIN...END — this is what makes it "inline"
AS
RETURN
(
    SELECT
        o.OrderId,
        o.OrderDate,
        o.TotalAmount,
        o.Status,
        c.Name AS CustomerName
    FROM Orders o
    JOIN Customers c ON o.CustomerId = c.CustomerId
    WHERE o.CustomerId = @CustomerId
      AND (@StartDate IS NULL OR o.OrderDate >= @StartDate)
);
GO

-- Usage — treated exactly like a table
SELECT * FROM dbo.fn_GetCustomerOrders(42, '2024-01-01');

-- Can be joined like a table (this is the power of iTVFs)
SELECT c.Name, f.OrderId, f.TotalAmount
FROM Customers c
CROSS APPLY dbo.fn_GetCustomerOrders(c.CustomerId, '2024-01-01') f
WHERE c.Country = 'India';

Multi-Statement Table-Valued Function (mTVF)

Returns a table but uses BEGIN...END with explicit INSERT statements to build the result. The optimizer cannot look inside — it always estimates 1 row (or a fixed guess). Performance can be poor for large results.

CREATE FUNCTION dbo.fn_GetEmployeeHierarchy
(
    @ManagerId INT
)
RETURNS @Result TABLE
(
    EmployeeId INT,
    Name       NVARCHAR(200),
    Level      INT
)
AS
BEGIN
    -- Insert the manager
    INSERT INTO @Result
    SELECT EmployeeId, Name, 0
    FROM Employees
    WHERE EmployeeId = @ManagerId;

    -- Loop to add subordinates (simplified — use recursive CTE in production)
    DECLARE @Level INT = 0;

    WHILE EXISTS (SELECT 1 FROM Employees e JOIN @Result r ON e.ManagerId = r.EmployeeId WHERE r.Level = @Level)
    BEGIN
        INSERT INTO @Result
        SELECT e.EmployeeId, e.Name, @Level + 1
        FROM Employees e
        JOIN @Result r ON e.ManagerId = r.EmployeeId
        WHERE r.Level = @Level;

        SET @Level += 1;
    END

    RETURN;
END;
GO

-- Usage
SELECT * FROM dbo.fn_GetEmployeeHierarchy(1);

Prefer iTVF over mTVF whenever possible. The performance difference is significant on large datasets.

APPLY Operator — Using Functions Row by Row

APPLY lets you call a table-valued function for each row of a table — it is like a JOIN where the right side is computed per row.

-- CROSS APPLY — like INNER JOIN: only rows where the function returns results
SELECT c.Name, o.OrderId, o.TotalAmount
FROM Customers c
CROSS APPLY dbo.fn_GetCustomerOrders(c.CustomerId, '2024-01-01') o;
-- Customers with no orders in 2024 are excluded

-- OUTER APPLY — like LEFT JOIN: all left rows, NULLs if function returns nothing
SELECT c.Name, o.OrderId, o.TotalAmount
FROM Customers c
OUTER APPLY dbo.fn_GetCustomerOrders(c.CustomerId, '2024-01-01') o;
-- Customers with no orders still appear with NULL order columns

-- CROSS APPLY without a function (derived table per row)
-- Get the most recent order for each customer
SELECT c.Name, recent.OrderId, recent.TotalAmount, recent.OrderDate
FROM Customers c
CROSS APPLY (
    SELECT TOP 1 OrderId, TotalAmount, OrderDate
    FROM Orders
    WHERE CustomerId = c.CustomerId
    ORDER BY OrderDate DESC
) recent;
-- The subquery references c.CustomerId from the outer query — this is APPLY's power
-- A regular subquery in FROM cannot reference the outer table

Window Functions — OVER()

Window functions compute a value for each row based on a “window” of related rows defined by the OVER clause. Unlike GROUP BY, they do not collapse rows.

-- PARTITION BY: defines the window groups (like GROUP BY but rows stay separate)
-- ORDER BY:     defines the order within each partition
-- ROWS/RANGE:   defines which rows in the partition are included (the frame)

SELECT
    OrderId,
    CustomerId,
    TotalAmount,
    OrderDate,

    -- Ranking
    ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY OrderDate)    AS OrderSequence,
    RANK()       OVER (PARTITION BY CustomerId ORDER BY TotalAmount DESC) AS SpendRank,
    DENSE_RANK() OVER (ORDER BY TotalAmount DESC)                     AS GlobalSpendRank,
    NTILE(4)     OVER (ORDER BY TotalAmount DESC)                     AS Quartile,

    -- Aggregation over a window (no GROUP BY needed)
    SUM(TotalAmount)   OVER (PARTITION BY CustomerId)                 AS CustomerTotal,
    AVG(TotalAmount)   OVER (PARTITION BY CustomerId)                 AS CustomerAvg,
    COUNT(*)           OVER ()                                        AS TotalOrderCount,

    -- Running total (cumulative)
    SUM(TotalAmount)   OVER (
        PARTITION BY CustomerId
        ORDER BY OrderDate
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS RunningTotal,

    -- Moving average (last 3 orders)
    AVG(TotalAmount)   OVER (
        PARTITION BY CustomerId
        ORDER BY OrderDate
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS MovingAvg3,

    -- Access values from other rows
    LAG(TotalAmount, 1, 0)  OVER (PARTITION BY CustomerId ORDER BY OrderDate) AS PrevOrderAmount,
    LEAD(TotalAmount, 1, 0) OVER (PARTITION BY CustomerId ORDER BY OrderDate) AS NextOrderAmount,
    FIRST_VALUE(TotalAmount) OVER (PARTITION BY CustomerId ORDER BY OrderDate) AS FirstOrderAmount,
    LAST_VALUE(TotalAmount)  OVER (
        PARTITION BY CustomerId
        ORDER BY OrderDate
        ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
    ) AS LastOrderAmount

FROM Orders
ORDER BY CustomerId, OrderDate;

5. Interview Questions and Answers

CTE vs Temp Table

Q: What is a CTE and when would you use it over a subquery?

A CTE (Common Table Expression) is a named, temporary result set defined with the WITH keyword at the start of a query. It is not stored physically — it is a logical construct. Use a CTE instead of a subquery when the same subquery needs to be referenced multiple times in the same query, when the query has multiple steps that benefit from being named for readability, or when you need recursion for hierarchical data. A subquery embedded inline in a SELECT or FROM clause becomes hard to read when complex; a CTE gives it a clear name.

Q: What is a recursive CTE and what is it used for?

A recursive CTE references itself in its own definition. It has two parts separated by UNION ALL: the anchor member (the base case, the starting rows) and the recursive member (which joins back to the CTE itself to find the next level). SQL Server executes the anchor, then repeatedly executes the recursive member using the previous iteration’s results, until no more rows are returned. It is used for hierarchical data: org charts, category trees, bill of materials, and generating sequences like date ranges.

Q: When would you choose a temp table over a CTE?

Choose a temp table when the intermediate result set is large and will be queried multiple times, when you need to add an index on the intermediate data for performance, when SQL Server’s execution plan estimate for the intermediate result is poor (CTEs have no statistics), or when the intermediate result needs to be manipulated further with INSERT, UPDATE, or DELETE. CTEs are recomputed every time they are referenced if referenced more than once, whereas a temp table stores the result once.

Q: What is the difference between a temp table and a table variable?

Both are temporary storage. A temp table (#table) is stored in tempdb with physical pages, can have indexes, and SQL Server builds statistics on it for accurate query planning. It is scoped to the session. A table variable (@table) is in memory (spills to tempdb when large), cannot have indexes beyond a primary key, and SQL Server always estimates it has 1 row regardless of actual size — which can produce poor execution plans for large datasets. Table variables survive ROLLBACK; temp tables do not.

JOINs

Q: What is the difference between INNER JOIN and LEFT JOIN?

INNER JOIN returns only the rows where both tables have a match on the join condition. Rows in either table with no corresponding match are excluded. LEFT JOIN returns all rows from the left table, plus the matching rows from the right table. Where the left table has no match in the right table, the right table columns appear as NULL. Use LEFT JOIN when you want to preserve all rows from the left table regardless of whether a match exists.

Q: What is a CROSS JOIN and when would you use it?

A CROSS JOIN returns every possible combination of rows from both tables — the Cartesian product. There is no join condition. If the left table has 10 rows and the right has 5, the result has 50 rows. Use it for generating combinations (sizes x colors, employees x shifts), pairing every row with a constant value (using a single-row CTE), or generating test data.

Q: How do you find rows that exist in one table but not another?

There are three common patterns. The LEFT JOIN + IS NULL pattern joins the two tables with a LEFT JOIN and filters for NULL on the right side’s key column. The NOT EXISTS pattern uses a correlated subquery to check for absence. The NOT IN pattern works but has a silent NULL bug — if the subquery returns any NULL, NOT IN returns no rows at all. In production, prefer NOT EXISTS as it is both correct and usually efficient.

Q: What is a self join?

A self join joins a table to itself using two different aliases. It is used when rows in a table have a relationship with other rows in the same table. The classic example is an Employees table where each employee has a ManagerId that references another EmployeeId in the same table. You join Employees to itself, aliased as e for employees and m for managers, to get each employee alongside their manager’s name.

GROUP BY and HAVING

Q: What is the difference between WHERE and HAVING?

WHERE filters individual rows before they are grouped. It operates on the raw table data and cannot reference aggregate functions. HAVING filters groups after GROUP BY has been applied. It operates on the grouped results and can reference aggregate functions like COUNT, SUM, and AVG. A common mistake is using HAVING for conditions that could be in WHERE — this forces SQL Server to compute the aggregation for all rows before discarding groups, instead of discarding rows before aggregation.

Q: In what order does SQL Server execute the clauses of a SELECT statement?

The logical execution order is: FROM, JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, and finally TOP or OFFSET-FETCH. This order explains several common confusions: you cannot use a column alias defined in SELECT inside WHERE (WHERE executes before SELECT), you cannot filter aggregates in WHERE (you need HAVING, which executes after GROUP BY), and ORDER BY can reference aliases from SELECT because it executes after SELECT.

Q: What is the difference between ROW_NUMBER, RANK, and DENSE_RANK?

All three assign a number to rows within a partition ordered by some column. ROW_NUMBER always assigns a unique sequential number with no ties and no gaps. RANK assigns the same number to rows with equal values but skips numbers after a tie group — if two rows share rank 2, the next rank is 4, not 3. DENSE_RANK also assigns the same number to ties but does not skip — if two rows share rank 2, the next rank is 3. Use ROW_NUMBER when you need exactly one row per group, RANK when tied rows should share a position with gaps, and DENSE_RANK when tied rows share a position without gaps.

Functions

Q: What is the difference between a scalar function and an inline table-valued function?

A scalar function returns a single value and has a BEGIN…END block. When called in a SELECT clause on a large table, it executes once per row — which is extremely slow on large datasets. An inline table-valued function (iTVF) returns a table, uses a single RETURN statement without BEGIN…END, and the SQL Server optimizer can look inside it and merge it into the calling query’s execution plan. iTVFs are as fast as writing the SQL inline. They can also be used with CROSS APPLY and OUTER APPLY to call them per row efficiently.

Q: What is APPLY and how is it different from JOIN?

APPLY allows you to invoke a table-valued function or a correlated subquery for each row of the outer table. CROSS APPLY is like INNER JOIN — only returns rows where the function produces results. OUTER APPLY is like LEFT JOIN — returns all outer rows, with NULLs if the function produces nothing. The key difference from JOIN is that the right side of APPLY can reference columns from the left side — it is evaluated per row. A regular JOIN’s right table expression cannot reference the left table.

Q: What is COALESCE and how does it differ from ISNULL?

COALESCE returns the first non-NULL value from a list of arguments. It is ANSI standard SQL, accepts any number of arguments, and the return type is the highest precedence type among its arguments. ISNULL is SQL Server-specific, accepts exactly two arguments, and always returns the data type of the first argument. ISNULL(NULL, 0) returns an INT. COALESCE(NULL, 0.5) returns a FLOAT because FLOAT has higher precedence than INT. In practice, COALESCE is more flexible and more portable.

Q: What does NULLIF do and why is it useful?

NULLIF takes two arguments and returns NULL if they are equal, or the first argument if they differ. Its most common use is preventing divide-by-zero errors: TotalRevenue / NULLIF(OrderCount, 0) — if OrderCount is 0, NULLIF returns NULL, making the entire division NULL instead of throwing an error. It is also used to convert sentinel values (like empty strings used as stand-ins for NULL) back to actual NULL: NULLIF(PhoneNumber, '') returns NULL when the phone number is an empty string.

Quick Reference Cheat Sheet

CTE vs Temp Table vs Table Variable

Use CTE when:
    Single use, immediately followed by main query
    Readability — complex logic needs a clear name
    Recursion needed (only option)
    Small intermediate result

Use Temp Table when:
    Large intermediate result (thousands of rows+)
    Used multiple times in the same procedure
    Needs an index for performance
    Accurate statistics matter for the optimizer

Use Table Variable when:
    Small dataset (a few hundred rows)
    Short lifecycle within a procedure
    Should survive a ROLLBACK

JOIN Types at a Glance

INNER JOIN    Both tables must match         -- Most common
LEFT JOIN     All left + matched right       -- Preserve left side
RIGHT JOIN    All right + matched left       -- Rarely used (flip to LEFT JOIN)
FULL OUTER    Everything from both sides     -- Find orphans on both sides
CROSS JOIN    Every combination              -- Cartesian product
SELF JOIN     Table joined to itself         -- Hierarchies in one table

WHERE vs HAVING

WHERE   -> row-level filter -> before GROUP BY -> can use index -> fast
HAVING  -> group-level filter -> after GROUP BY -> must compute aggregate first

Rule: put everything that does not involve aggregates in WHERE.
      Only use HAVING for aggregate conditions.

Window Function Frame Clauses

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW  -- Running total from start
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW          -- Moving window of last 3 rows
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING   -- Needed for LAST_VALUE to work correctly
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING -- Entire partition

NULL Handling Functions

ISNULL(col, default)              -- Replace NULL with default (SQL Server only, 2 args)
COALESCE(a, b, c, ...)            -- First non-NULL from the list (ANSI, any number of args)
NULLIF(a, b)                      -- Returns NULL if a = b, else returns a
TRY_CAST(value AS type)           -- Safe cast, returns NULL on failure (no error)
TRY_CONVERT(type, value)          -- Safe convert, returns NULL on failure

These four areas — CTE, JOINs, GROUP BY with HAVING, and Functions — are the engine room of real SQL work. Every reporting query, every data transformation, every performance problem eventually comes back to one of these. Understand them deeply and you will write SQL that is both correct and fast.
