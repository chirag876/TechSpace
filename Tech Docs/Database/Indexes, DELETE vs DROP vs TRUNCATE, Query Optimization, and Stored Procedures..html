1. Indexes

What Is an Index?

Imagine a textbook with 1000 pages. You need to find every mention of “foreign key.” Without an index at the back of the book, you read every single page. With an index, you flip to “F”, find “foreign key — pages 45, 312, 678”, and go directly there.

A database index works exactly the same way. Without an index, SQL Server reads every row in the table (a full table scan) to find what you are looking for. With an index, it jumps directly to the relevant rows. On a table with ten million rows, this is the difference between a query that takes 45 seconds and one that takes 2 milliseconds.

How SQL Server Stores Data — The Heap and the B-Tree

Before understanding indexes, you need to know how SQL Server physically stores data.

Heap: A table with no clustered index. Data pages are stored in no particular order. Finding rows requires scanning every page — a full table scan every time.

B-Tree (Balanced Tree): The data structure used for indexes. It is a tree where:

  • The root node contains pointers to intermediate nodes
  • Intermediate nodes contain pointers to leaf nodes
  • Leaf nodes contain the actual data (or pointers to it)

Every level of the tree has the same height — “balanced.” A search starts at the root and traverses down to the leaf in O(log n) time. A table with 10 million rows needs at most about 24 comparisons to find any row.

B-Tree Structure:

                    [Root: 500]
                   /            \
        [250]                   [750]
       /     \                 /     \
  [100][200]  [300][400]  [600][700]  [800][900]
   |    |      |    |      |    |      |    |
  Rows Rows   Rows Rows   Rows Rows   Rows Rows

Clustered Index

A clustered index determines the physical order of data in the table. The table IS the index. The leaf nodes of the B-Tree contain the actual data rows.

There can be only one clustered index per table because data can only be physically sorted one way.

-- Creating a clustered index (usually done via PRIMARY KEY automatically)
CREATE TABLE Orders
(
    OrderId     INT         NOT NULL,
    CustomerId  INT         NOT NULL,
    OrderDate   DATETIME    NOT NULL,
    TotalAmount DECIMAL(18,2) NOT NULL,

    CONSTRAINT PK_Orders PRIMARY KEY CLUSTERED (OrderId)
    -- This creates a clustered index on OrderId automatically
);

-- Explicit clustered index creation
CREATE CLUSTERED INDEX CIX_Orders_OrderDate
ON Orders (OrderDate);

-- Check existing indexes on a table
EXEC sp_helpindex 'Orders';

-- Or use this view
SELECT
    i.name          AS IndexName,
    i.type_desc     AS IndexType,
    c.name          AS ColumnName,
    ic.key_ordinal  AS KeyOrder
FROM sys.indexes i
JOIN sys.index_columns ic ON i.object_id = ic.object_id AND i.index_id = ic.index_id
JOIN sys.columns c        ON ic.object_id = c.object_id AND ic.column_id = c.column_id
WHERE i.object_id = OBJECT_ID('Orders')
ORDER BY i.index_id, ic.key_ordinal;

How SQL Server finds a row with a clustered index:

-- SQL Server does a B-Tree traversal on OrderId
-- Root -> Intermediate -> Leaf (the actual data row)
-- Extremely fast
SELECT * FROM Orders WHERE OrderId = 50000;

-- Clustered index range scan — also fast
-- SQL Server finds OrderDate = '2024-01-01' and reads forward
SELECT * FROM Orders WHERE OrderDate BETWEEN '2024-01-01' AND '2024-01-31';

Nonclustered Index

A nonclustered index is a separate structure from the table data. The leaf nodes contain the indexed column values plus a row locator — either the clustered index key (if a clustered index exists) or the actual physical row pointer (if no clustered index exists, i.e., a heap).

You can have up to 999 nonclustered indexes on a table (though having that many is a sign of a design problem).

-- Simple nonclustered index on a single column
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON Orders (CustomerId);

-- Nonclustered index on multiple columns (composite index)
CREATE NONCLUSTERED INDEX IX_Orders_CustomerDate
ON Orders (CustomerId, OrderDate);

-- The order of columns in a composite index matters critically
-- This index is useful for:
--   WHERE CustomerId = 5
--   WHERE CustomerId = 5 AND OrderDate > '2024-01-01'
-- This index is NOT useful for:
--   WHERE OrderDate > '2024-01-01'  (CustomerId is not specified — leading column missing)

How SQL Server uses a nonclustered index:

-- Step 1: SQL Server searches the nonclustered index B-Tree for CustomerId = 42
--         This gives it the OrderId (clustered key) for all matching rows
-- Step 2: SQL Server does a Key Lookup — goes back to the clustered index
--         to fetch the remaining columns (OrderDate, TotalAmount, etc.)
-- This two-step process is called a Key Lookup or Bookmark Lookup
SELECT OrderDate, TotalAmount FROM Orders WHERE CustomerId = 42;

Covering Index and INCLUDE

The Key Lookup (going from the nonclustered index back to the clustered index to fetch more columns) is expensive when done for many rows. A covering index eliminates this by including all the columns the query needs directly in the index.

-- Without INCLUDE — requires a Key Lookup for OrderDate and TotalAmount
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON Orders (CustomerId);

-- With INCLUDE — the query is covered entirely by the index, no Key Lookup needed
-- The INCLUDE columns are stored in the leaf nodes but not part of the sort key
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId_Covering
ON Orders (CustomerId)
INCLUDE (OrderDate, TotalAmount);

-- This query can now be answered entirely from the index
-- SQL Server never needs to touch the actual table data
SELECT OrderDate, TotalAmount
FROM Orders
WHERE CustomerId = 42;

Key Column vs INCLUDE Column:

Key Columns INCLUDE Columns
Part of the B-Tree sort structure Only stored at the leaf level
Support equality and range predicates Only for covering — cannot be in WHERE
Affect index size at all levels Only increase leaf-level size
Max 16 columns, 900 bytes combined Up to 1023 non-key columns

Unique Index

A unique index enforces uniqueness — no two rows can have the same value(s) in the indexed columns.

-- Unique constraint automatically creates a unique nonclustered index
ALTER TABLE Users
ADD CONSTRAINT UQ_Users_Email UNIQUE (Email);

-- Explicit unique index
CREATE UNIQUE NONCLUSTERED INDEX UIX_Users_Email
ON Users (Email)
WHERE Email IS NOT NULL; -- Filtered unique index — NULL values are excluded
                          -- This allows multiple rows with NULL email

Filtered Index

A filtered index covers only a subset of rows. If your queries consistently filter on a specific condition, a filtered index is smaller and faster than a full index.

-- Only active orders get indexed — queries on active orders are fast
-- The index is far smaller than a full index on Status
CREATE NONCLUSTERED INDEX IX_Orders_Active
ON Orders (OrderDate, CustomerId)
WHERE Status = 'Active';

-- Useful for sparse data — columns that are NULL most of the time
CREATE NONCLUSTERED INDEX IX_Orders_HasDiscount
ON Orders (DiscountCode)
WHERE DiscountCode IS NOT NULL;
-- Only rows with a discount code are in the index
-- Queries filtering on DiscountCode IS NOT NULL are very fast

Columnstore Index

Traditional indexes are rowstore — data is stored row by row. A columnstore index stores data column by column, which is dramatically better for analytical queries that aggregate large datasets.

-- Nonclustered columnstore — the original table data is unchanged
-- Adds a column-oriented copy of the data for analytics
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Sales_Analytics
ON Sales (Year, Month, ProductId, Revenue, Quantity);

-- Clustered columnstore — the entire table is stored column-by-column
-- Best for pure data warehouse / reporting tables
CREATE CLUSTERED COLUMNSTORE INDEX CCI_FactSales
ON FactSales;

-- Queries like this become enormously faster with columnstore
SELECT
    ProductId,
    SUM(Revenue) AS TotalRevenue,
    AVG(Quantity) AS AvgQuantity
FROM Sales
WHERE Year = 2024
GROUP BY ProductId;

Columnstore indexes use batch mode execution (processing 900 rows at a time instead of one) and achieve compression ratios of 5x to 10x compared to rowstore.

Index Maintenance — Fragmentation

Over time, as rows are inserted, updated, and deleted, index pages become fragmented. The data in the B-Tree is no longer in contiguous pages on disk. This slows down range scans.

-- Check fragmentation
SELECT
    OBJECT_NAME(ips.object_id)      AS TableName,
    i.name                           AS IndexName,
    ips.avg_fragmentation_in_percent AS Fragmentation,
    ips.page_count                   AS PageCount
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 5
ORDER BY ips.avg_fragmentation_in_percent DESC;

-- Fix fragmentation
-- Under 30% fragmentation: REORGANIZE (online, low impact)
ALTER INDEX IX_Orders_CustomerId ON Orders REORGANIZE;

-- Over 30% fragmentation: REBUILD (offline by default, resets fragmentation to ~0%)
ALTER INDEX IX_Orders_CustomerId ON Orders REBUILD;

-- Rebuild all indexes on a table
ALTER INDEX ALL ON Orders REBUILD;

-- Online rebuild (Enterprise edition — table remains accessible during rebuild)
ALTER INDEX ALL ON Orders REBUILD WITH (ONLINE = ON);

The Cost of Too Many Indexes

Indexes are not free.

INSERT: Every index on the table must be updated. 10 indexes = 10 extra writes.
UPDATE: If the updated column is indexed, the old index entry is deleted and a new one inserted.
DELETE: The row must be removed from every index.
Storage: Every index consumes disk space.

A table with 20 indexes will have:
    Fast SELECT performance
    Slow INSERT/UPDATE/DELETE performance
    High storage usage
    High maintenance overhead

The sweet spot: index the columns actually used in WHERE, JOIN, and ORDER BY
in your most frequent and critical queries. No more, no less.

Finding Missing Indexes

SQL Server tracks queries and suggests missing indexes based on actual execution patterns.

-- Indexes SQL Server wishes existed (based on query execution history)
SELECT TOP 10
    migs.avg_total_user_cost * migs.avg_user_impact * (migs.user_seeks + migs.user_scans) AS ImprovementMeasure,
    mid.statement                   AS TableName,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns,
    migs.user_seeks,
    migs.user_scans,
    migs.avg_user_impact
FROM sys.dm_db_missing_index_details mid
JOIN sys.dm_db_missing_index_groups mig  ON mid.index_handle = mig.index_handle
JOIN sys.dm_db_missing_index_group_stats migs ON mig.index_group_handle = migs.group_handle
ORDER BY ImprovementMeasure DESC;

-- Index usage statistics — find unused indexes (candidates for removal)
SELECT
    OBJECT_NAME(i.object_id)    AS TableName,
    i.name                       AS IndexName,
    ius.user_seeks,
    ius.user_scans,
    ius.user_lookups,
    ius.user_updates,
    ius.last_user_seek,
    ius.last_user_scan
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats ius
    ON i.object_id = ius.object_id AND i.index_id = ius.index_id
    AND ius.database_id = DB_ID()
WHERE OBJECT_NAME(i.object_id) = 'Orders'
ORDER BY (ISNULL(ius.user_seeks, 0) + ISNULL(ius.user_scans, 0)) ASC;

2. DELETE, DROP, and TRUNCATE

These three words sound similar and all “remove” things, but they operate at completely different levels, have different rollback behaviour, and are appropriate in completely different situations.

The analogy:

  • DELETE is removing specific books from a library shelf. The shelf stays. You can undo it.
  • TRUNCATE is clearing an entire shelf completely and resetting the shelf’s numbering. The shelf stays. Hard to undo.
  • DROP is demolishing the entire shelf, the cabinet, and the blueprints. Everything is gone.

DELETE — Surgical Removal

DELETE removes rows from a table. You can specify exactly which rows with a WHERE clause. It is fully logged — every deleted row is written to the transaction log. It fires DELETE triggers. It can be rolled back.

-- Delete specific rows
DELETE FROM Orders
WHERE Status = 'Cancelled' AND OrderDate < '2022-01-01';

-- Delete with a JOIN (delete orders belonging to inactive customers)
DELETE o
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
WHERE c.IsActive = 0;

-- Delete with subquery
DELETE FROM OrderItems
WHERE OrderId IN (
    SELECT OrderId FROM Orders WHERE Status = 'Cancelled'
);

-- Delete all rows (no WHERE — dangerous, but valid)
DELETE FROM TempData;

-- DELETE is transactional — you can roll it back
BEGIN TRANSACTION;

DELETE FROM Orders WHERE OrderId = 999;

-- Changed your mind
ROLLBACK TRANSACTION;
-- The row is back

-- Or keep it
COMMIT TRANSACTION;

OUTPUT clause — see what you deleted:

-- Capture deleted rows before they are gone
DELETE FROM Orders
OUTPUT DELETED.OrderId, DELETED.CustomerId, DELETED.TotalAmount
WHERE Status = 'Cancelled';

-- Insert deleted rows into an archive table
DELETE FROM Orders
OUTPUT DELETED.*
INTO OrdersArchive
WHERE Status = 'Cancelled' AND OrderDate < '2023-01-01';

TRUNCATE — The Full Wipe

TRUNCATE removes all rows from a table. You cannot specify a WHERE clause — it is all or nothing. It is minimally logged (records page deallocations, not individual row deletions). It does not fire DELETE triggers. It resets the identity counter. It is dramatically faster than DELETE for large tables.

-- Remove all rows from the table
TRUNCATE TABLE TempProcessingData;

-- TRUNCATE resets the identity seed
-- After TRUNCATE, the next INSERT gets Id = 1 again
-- After DELETE FROM table, the identity continues from where it was

-- TRUNCATE is still transactional — you CAN roll it back
BEGIN TRANSACTION;
TRUNCATE TABLE StagingData;
ROLLBACK TRANSACTION; -- The data is back

-- TRUNCATE cannot be used if:
-- 1. The table is referenced by a FOREIGN KEY constraint (even if the child table is empty)
-- 2. The table participates in an indexed view
-- 3. The table is published using transactional or merge replication

-- If a foreign key references this table, TRUNCATE fails:
TRUNCATE TABLE Customers;
-- Error: Cannot truncate table 'Customers' because it is being referenced by a FOREIGN KEY constraint.
-- You must drop the FK, truncate, then recreate the FK
-- OR use DELETE FROM Customers (slower but works)

DROP — The Demolition

DROP removes the database object entirely — the table, its data, its indexes, its constraints, its triggers, its statistics. Everything. The object no longer exists.

-- Drop a table completely
DROP TABLE Orders;
-- The table, all its rows, all its indexes, all its constraints are gone

-- Drop only if it exists (prevents error if run again)
DROP TABLE IF EXISTS TempResults;

-- Drop other objects
DROP INDEX IX_Orders_CustomerId ON Orders;
DROP VIEW  vw_ActiveOrders;
DROP PROCEDURE sp_GetOrdersByCustomer;
DROP FUNCTION fn_GetOrderTotal;
DROP DATABASE OldDatabase; -- Drops the entire database

-- DROP is logged but the effect is immediate and irreversible
-- You cannot ROLLBACK a DROP outside of an explicit transaction
BEGIN TRANSACTION;
DROP TABLE Orders;
ROLLBACK TRANSACTION; -- The table comes back ONLY because of the explicit transaction
-- Without the BEGIN TRANSACTION wrapper, DROP is permanent

Side-by-Side Comparison

Feature DELETE TRUNCATE DROP
What it removes Specific rows (or all rows) All rows The entire object
WHERE clause Yes No No
Transaction log Fully logged (every row) Minimally logged (pages) Logged
Rollback possible Yes Yes (within transaction) Yes (within transaction)
Triggers fired Yes (DELETE triggers) No No
Identity reset No Yes Object is gone
Foreign key constraint Not blocked Blocked if referenced Blocked if referenced
Speed (large table) Slow Very fast Very fast
Table still exists after Yes Yes No
Permissions needed DELETE on table ALTER TABLE DROP permission

Which One to Use When

Remove specific rows based on a condition          -> DELETE with WHERE
Remove all rows but keep the table structure       -> TRUNCATE (if no FK constraints)
Remove all rows but keep identity counter          -> DELETE FROM table (no WHERE)
Clear a staging / temp table before reloading      -> TRUNCATE
Remove a table you no longer need at all           -> DROP
Remove a table temporarily (will recreate it)      -> DROP TABLE + CREATE TABLE
                                                      or TRUNCATE (cleaner)
Archive rows before deleting them                  -> DELETE with OUTPUT INTO

Practical Example — ETL Pipeline

-- Common pattern in ETL (Extract, Transform, Load) pipelines

-- Step 1: Clear the staging table for fresh data (fast, resets identity)
TRUNCATE TABLE Staging_Orders;

-- Step 2: Load fresh data into staging
BULK INSERT Staging_Orders
FROM 'C:\data\orders_today.csv'
WITH (FIELDTERMINATOR = ',', ROWTERMINATOR = '\n', FIRSTROW = 2);

-- Step 3: Delete old records from production that match today's data
DELETE p
FROM Production_Orders p
JOIN Staging_Orders s ON p.OrderId = s.OrderId;

-- Step 4: Insert fresh records
INSERT INTO Production_Orders
SELECT * FROM Staging_Orders;

-- Step 5: Drop temp tables that were created just for this process
DROP TABLE IF EXISTS #TempCalculations;

3. SQL Optimization

Why Queries Get Slow

A slow query is not bad luck. It has a reason. Understanding the reason is how you fix it.

The most common culprits:

1. Full table scan (no index for the WHERE clause)
2. Index exists but query cannot use it (non-sargable predicate)
3. Wrong join order or missing indexes on join columns
4. SELECT * fetching columns you do not need
5. N+1 query pattern (query inside a loop)
6. Parameter sniffing — bad execution plan cached from an unusual parameter value
7. Implicit type conversion (comparing INT to VARCHAR — kills index usage)
8. Missing or outdated statistics
9. Too many rows returned when only a few are needed (missing TOP or pagination)
10. Locks and blocking (concurrency problems)

The Execution Plan — Your Best Friend

Before optimising anything, look at the execution plan. It shows you exactly what SQL Server is doing — which indexes it is using, where it is doing table scans, what is costing the most.

-- Show actual execution plan (runs the query and captures real stats)
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT o.OrderId, o.OrderDate, c.Name
FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
WHERE o.OrderDate > '2024-01-01';

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

-- Output includes:
-- Table 'Orders'. Scan count 1, logical reads 8432  <-- 8432 page reads = expensive
-- SQL Server Execution Times: CPU time = 1250 ms, elapsed time = 1843 ms

In SSMS: press Ctrl+M (Include Actual Execution Plan) before running the query. Look for:

  • Table Scan / Clustered Index Scan — reading the whole table (often bad for large tables)
  • Index Seek — using an index efficiently (what you want)
  • Key Lookup — going back to the main table after using a nonclustered index (expensive at scale)
  • Nested Loops / Hash Match / Merge Join — different join algorithms SQL Server chose
  • Fat arrows — thick arrows between operators = many rows flowing = potential problem
  • Warning triangles — SQL Server detected something wrong (implicit conversion, missing stats)

SARGable Predicates — Write Conditions That Use Indexes

SARG = Search ARGument able. A predicate is SARGable if SQL Server can use an index seek to evaluate it. If it is not SARGable, SQL Server must scan the entire table.

The rule: Do not wrap the indexed column in a function or expression on the left side of the condition. The column must be alone.

-- NON-SARGable — SQL Server cannot use an index on OrderDate
-- It must evaluate YEAR(OrderDate) for every single row (full scan)
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024;
SELECT * FROM Orders WHERE MONTH(OrderDate) = 6;
SELECT * FROM Orders WHERE DATEPART(YEAR, OrderDate) = 2024;
SELECT * FROM Orders WHERE CONVERT(VARCHAR, OrderDate, 103) = '01/06/2024';
SELECT * FROM Orders WHERE OrderId + 1 = 500;
SELECT * FROM Orders WHERE LEFT(CustomerName, 3) = 'Ali';

-- SARGable equivalents — SQL Server can seek in the index
SELECT * FROM Orders WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';
SELECT * FROM Orders WHERE OrderDate >= '2024-06-01' AND OrderDate < '2024-07-01';
SELECT * FROM Orders WHERE OrderId = 499;
SELECT * FROM Orders WHERE CustomerName LIKE 'Ali%'; -- Leading wildcard is SARGable
                                                      -- '%Ali%' is NOT SARGable

-- The pattern: move any transformation to the right side (the value), not the column
-- BAD:  WHERE UPPER(Email) = 'USER@EMAIL.COM'
-- GOOD: WHERE Email = 'user@email.com'  (store emails lowercase, or use a case-insensitive collation)

Implicit Type Conversion

When comparing columns of different data types, SQL Server silently converts one to match the other. This conversion prevents index usage.

-- The CustomerId column is INT. You pass a VARCHAR.
-- SQL Server converts every CustomerId in the table to VARCHAR to compare
-- Full table scan. Index is ignored.
SELECT * FROM Orders WHERE CustomerId = '42';  -- String vs INT

-- Correct — use matching types
SELECT * FROM Orders WHERE CustomerId = 42;

-- This happens in application code too
-- C#: command.Parameters.AddWithValue("@Id", "42")  -- string!
-- Should be: command.Parameters.Add("@Id", SqlDbType.Int).Value = 42

-- Check for implicit conversions in execution plan:
-- Look for CONVERT_IMPLICIT warnings (yellow triangle in SSMS)

SELECT * — The Lazy Killer

-- BAD — fetches every column, including columns you never use
-- Prevents covering indexes from working (always requires table access)
-- Breaks code if columns are added or reordered
-- Transfers unnecessary data over the network
SELECT * FROM Orders WHERE CustomerId = 42;

-- GOOD — fetch only what you need
SELECT OrderId, OrderDate, TotalAmount
FROM Orders
WHERE CustomerId = 42;

-- With a covering index on (CustomerId) INCLUDE (OrderDate, TotalAmount)
-- This query never touches the table data — answered entirely from the index

JOIN Optimisation

-- Always join on indexed columns
-- The join columns should have indexes on BOTH tables

-- Make sure data types match on join columns (implicit conversion kills performance)
-- BAD: joining Orders.CustomerId (INT) to Customers.Id (BIGINT) — implicit conversion
-- GOOD: same data types on both sides

-- Avoid functions on join columns
-- BAD
SELECT * FROM Orders o
JOIN Customers c ON LOWER(o.CustomerEmail) = LOWER(c.Email);

-- GOOD — store emails consistently, or fix at insert time
SELECT * FROM Orders o
JOIN Customers c ON o.CustomerEmail = c.Email;  -- With case-insensitive collation

-- Filter early — put WHERE conditions before the join reduces rows joined
-- SQL Server's optimizer usually handles this, but explicit subquery helps in complex cases
SELECT o.OrderId, o.TotalAmount, c.Name
FROM (
    SELECT OrderId, CustomerId, TotalAmount
    FROM Orders
    WHERE OrderDate > '2024-01-01'  -- Filter first, then join
) o
JOIN Customers c ON o.CustomerId = c.CustomerId;

EXISTS vs IN vs JOIN — Which to Use

-- Checking if related rows exist — use EXISTS
-- EXISTS stops as soon as it finds one match (short-circuits)
SELECT CustomerId, Name
FROM Customers c
WHERE EXISTS (
    SELECT 1 FROM Orders o WHERE o.CustomerId = c.CustomerId
);

-- IN with a subquery — works but can be slow for large subquery results
-- If the subquery returns NULLs, IN behaves unexpectedly
SELECT * FROM Orders
WHERE CustomerId IN (SELECT CustomerId FROM Customers WHERE Country = 'India');

-- JOIN — typically the most efficient for large datasets, gives you access to both tables
SELECT DISTINCT c.CustomerId, c.Name
FROM Customers c
JOIN Orders o ON c.CustomerId = o.CustomerId
WHERE c.Country = 'India';

-- NOT EXISTS is almost always faster than NOT IN
-- NOT IN with a subquery that returns NULL values excludes ALL rows (logical trap)
-- BAD
SELECT * FROM Customers
WHERE CustomerId NOT IN (SELECT CustomerId FROM Orders);
-- If any Order has NULL CustomerId, this returns zero rows — a hidden bug

-- GOOD
SELECT * FROM Customers c
WHERE NOT EXISTS (
    SELECT 1 FROM Orders o WHERE o.CustomerId = c.CustomerId
);

TOP and Pagination

-- Get the first N rows — stops scanning once N rows are found
SELECT TOP 10 OrderId, OrderDate, TotalAmount
FROM Orders
WHERE Status = 'Pending'
ORDER BY OrderDate DESC;

-- Pagination with OFFSET/FETCH (SQL Server 2012+)
-- Page 3, 20 rows per page
SELECT OrderId, OrderDate, TotalAmount
FROM Orders
ORDER BY OrderDate DESC
OFFSET 40 ROWS        -- Skip the first 40 rows (pages 1 and 2)
FETCH NEXT 20 ROWS ONLY; -- Return the next 20 rows

-- Keyset pagination (faster for large offsets)
-- Instead of skipping rows, continue from where you left off
-- Last row on previous page had OrderDate = '2024-05-10', OrderId = 12345
SELECT TOP 20 OrderId, OrderDate, TotalAmount
FROM Orders
WHERE OrderDate < '2024-05-10'
   OR (OrderDate = '2024-05-10' AND OrderId < 12345)
ORDER BY OrderDate DESC, OrderId DESC;
-- This uses an index seek instead of scanning and skipping rows

CTEs and Avoiding Repeated Subqueries

-- Repeated subquery — evaluated multiple times (SQL Server may or may not cache it)
SELECT
    OrderId,
    TotalAmount,
    TotalAmount / (SELECT SUM(TotalAmount) FROM Orders WHERE YEAR(OrderDate) = 2024) AS PctOfTotal
FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- CTE — defined once, referenced multiple times
WITH YearlyTotal AS (
    SELECT SUM(TotalAmount) AS Total
    FROM Orders
    WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
)
SELECT
    o.OrderId,
    o.TotalAmount,
    o.TotalAmount / yt.Total AS PctOfTotal
FROM Orders o
CROSS JOIN YearlyTotal yt
WHERE o.OrderDate >= '2024-01-01' AND o.OrderDate < '2025-01-01';

Avoiding Cursors — Set-Based Operations

SQL Server is designed to operate on sets of rows at once. Cursors process one row at a time in a loop. On large datasets, cursors can be 100x slower than equivalent set-based operations.

-- CURSOR approach — processes one row at a time (slow)
DECLARE @OrderId INT, @CustomerId INT;
DECLARE order_cursor CURSOR FOR
    SELECT OrderId, CustomerId FROM Orders WHERE Status = 'Pending';

OPEN order_cursor;
FETCH NEXT FROM order_cursor INTO @OrderId, @CustomerId;

WHILE @@FETCH_STATUS = 0
BEGIN
    UPDATE Orders SET Status = 'Processing' WHERE OrderId = @OrderId;
    -- Some per-row logic...
    FETCH NEXT FROM order_cursor INTO @OrderId, @CustomerId;
END

CLOSE order_cursor;
DEALLOCATE order_cursor;

-- SET-BASED equivalent — processes all rows at once (fast)
UPDATE Orders
SET Status = 'Processing'
WHERE Status = 'Pending';

-- When you think you need a cursor, ask:
-- Can this be done with UPDATE ... FROM?
-- Can this be done with a CTE and ROW_NUMBER()?
-- Can this be done with CASE expressions?
-- 90% of the time, the answer is yes.

Temp Tables vs Table Variables vs CTEs

-- CTE — defined inline, no physical storage, used once in a query
-- Good for readability and simple one-time transformations
WITH RecentOrders AS (
    SELECT * FROM Orders WHERE OrderDate > '2024-01-01'
)
SELECT * FROM RecentOrders WHERE TotalAmount > 1000;

-- Table Variable — stored in memory (and tempdb if large), scoped to batch
-- No statistics — optimizer assumes 1 row regardless of actual count
-- Good for small datasets (< a few thousand rows)
DECLARE @RecentOrders TABLE (OrderId INT, TotalAmount DECIMAL(18,2));
INSERT INTO @RecentOrders
SELECT OrderId, TotalAmount FROM Orders WHERE OrderDate > '2024-01-01';

SELECT * FROM @RecentOrders WHERE TotalAmount > 1000;

-- Temp Table — stored in tempdb, can have indexes and statistics
-- SQL Server can build an accurate execution plan for queries against them
-- Good for large datasets or when you need to query the data multiple times
CREATE TABLE #RecentOrders (OrderId INT, TotalAmount DECIMAL(18,2));
CREATE INDEX IX_Temp_TotalAmount ON #RecentOrders (TotalAmount);

INSERT INTO #RecentOrders
SELECT OrderId, TotalAmount FROM Orders WHERE OrderDate > '2024-01-01';

SELECT * FROM #RecentOrders WHERE TotalAmount > 1000;

DROP TABLE #RecentOrders; -- Clean up (dropped automatically when session ends)

Can have indexes No Limited Yes
Statistics No No (always 1 row estimate) Yes
Scope Single statement Batch / stored procedure Session
Good for Readability, one-time use Small datasets Large datasets, multiple uses

Statistics — What SQL Server Uses to Make Decisions

SQL Server keeps statistics on columns — histograms of data distribution. These statistics are used by the Query Optimizer to estimate how many rows a condition will return and choose the best execution plan.

-- View statistics for a table
DBCC SHOW_STATISTICS ('Orders', 'IX_Orders_CustomerId');

-- Update statistics manually (when auto-update is too infrequent for your workload)
UPDATE STATISTICS Orders;            -- All statistics on the table
UPDATE STATISTICS Orders IX_Orders_CustomerId; -- Specific index statistics
UPDATE STATISTICS Orders WITH FULLSCAN; -- Scan entire table (slower but most accurate)

-- Check when statistics were last updated
SELECT
    OBJECT_NAME(s.object_id)  AS TableName,
    s.name                     AS StatName,
    sp.last_updated,
    sp.rows,
    sp.rows_sampled
FROM sys.stats s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) sp
WHERE OBJECT_NAME(s.object_id) = 'Orders'
ORDER BY sp.last_updated DESC;

Query Hints — Use Sparingly

Query hints override the optimizer’s decisions. They are a last resort — usually you should fix the underlying data model, statistics, or query structure.

-- Force an index (when you know the optimizer is making a bad choice)
SELECT * FROM Orders WITH (INDEX(IX_Orders_CustomerId))
WHERE CustomerId = 42;

-- NOLOCK hint — reads uncommitted data (dirty reads), avoids locking
-- Fast but can return inconsistent data
-- Use only for approximate reporting queries where accuracy is not critical
SELECT COUNT(*) FROM Orders WITH (NOLOCK);

-- Recompile hint — forces a new execution plan every time (avoids parameter sniffing)
SELECT * FROM Orders WHERE CustomerId = @CustomerId
OPTION (RECOMPILE);

-- Force a specific join algorithm
SELECT * FROM Orders o
JOIN Customers c ON o.CustomerId = c.CustomerId
OPTION (HASH JOIN); -- or LOOP JOIN, MERGE JOIN

-- Maxdop — limit parallelism for a specific query
SELECT SUM(TotalAmount) FROM Orders
OPTION (MAXDOP 1); -- Single-threaded execution

4. Stored Procedures

What Is a Stored Procedure?

A stored procedure is a named, precompiled batch of SQL statements stored in the database. You call it by name, optionally passing parameters, and it executes.

Think of it as a function in your database. Instead of sending a full SQL query from your application every time, you send EXEC sp_GetOrdersByCustomer @CustomerId = 42 — a short, fast call.

Benefits:
    Precompiled execution plan — faster than ad-hoc SQL on first run
    Reduced network traffic — only parameter values travel over the wire
    Security — grant EXECUTE on the procedure without granting SELECT/INSERT/DELETE on tables
    Centralized logic — business rules enforced at the database level
    Reduced SQL injection surface — parameterised by nature

Drawbacks:
    Business logic split between application and database (hard to version control)
    Harder to unit test than application code
    Tightly coupled to SQL Server (hard to switch databases)
    Can become unmaintainable "stored procedure hell" if overused

Creating a Stored Procedure

-- Basic stored procedure
CREATE PROCEDURE sp_GetOrdersByCustomer
    @CustomerId INT
AS
BEGIN
    SET NOCOUNT ON; -- Suppresses "N rows affected" messages (minor performance improvement)

    SELECT
        o.OrderId,
        o.OrderDate,
        o.TotalAmount,
        o.Status
    FROM Orders o
    WHERE o.CustomerId = @CustomerId
    ORDER BY o.OrderDate DESC;
END;
GO

-- Call it
EXEC sp_GetOrdersByCustomer @CustomerId = 42;
-- or
EXEC sp_GetOrdersByCustomer 42; -- Positional — works but less readable

-- Modify it (ALTER preserves permissions; DROP + CREATE loses them)
ALTER PROCEDURE sp_GetOrdersByCustomer
    @CustomerId INT,
    @Status     NVARCHAR(50) = NULL -- Optional parameter with default value
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        o.OrderId,
        o.OrderDate,
        o.TotalAmount,
        o.Status
    FROM Orders o
    WHERE o.CustomerId = @CustomerId
      AND (@Status IS NULL OR o.Status = @Status) -- NULL means "ignore this filter"
    ORDER BY o.OrderDate DESC;
END;
GO

-- Call with optional parameter
EXEC sp_GetOrdersByCustomer @CustomerId = 42;                         -- All statuses
EXEC sp_GetOrdersByCustomer @CustomerId = 42, @Status = 'Confirmed';  -- Only Confirmed

Input, Output, and Return Values

CREATE PROCEDURE sp_PlaceOrder
    @CustomerId     INT,
    @TotalAmount    DECIMAL(18, 2),
    @NewOrderId     INT OUTPUT,       -- OUTPUT parameter — value set inside the procedure
    @ErrorMessage   NVARCHAR(500) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;

    -- Validate
    IF NOT EXISTS (SELECT 1 FROM Customers WHERE CustomerId = @CustomerId)
    BEGIN
        SET @ErrorMessage = 'Customer does not exist.';
        RETURN -1; -- Return code: non-zero means failure (convention)
    END

    -- Insert the order
    INSERT INTO Orders (CustomerId, TotalAmount, OrderDate, Status)
    VALUES (@CustomerId, @TotalAmount, GETDATE(), 'Pending');

    -- Set the output parameter to the new ID
    SET @NewOrderId = SCOPE_IDENTITY();
    SET @ErrorMessage = NULL;

    RETURN 0; -- Return code: 0 means success (convention)
END;
GO

-- Calling and capturing output parameters
DECLARE @NewId INT;
DECLARE @ErrMsg NVARCHAR(500);
DECLARE @ReturnCode INT;

EXEC @ReturnCode = sp_PlaceOrder
    @CustomerId  = 42,
    @TotalAmount = 1500.00,
    @NewOrderId  = @NewId OUTPUT,
    @ErrorMessage = @ErrMsg OUTPUT;

IF @ReturnCode = 0
    PRINT 'Order created with ID: ' + CAST(@NewId AS VARCHAR);
ELSE
    PRINT 'Error: ' + @ErrMsg;

Error Handling in Stored Procedures

CREATE PROCEDURE sp_TransferFunds
    @FromAccountId  INT,
    @ToAccountId    INT,
    @Amount         DECIMAL(18, 2)
AS
BEGIN
    SET NOCOUNT ON;

    -- Input validation
    IF @Amount <= 0
        THROW 50001, 'Transfer amount must be positive.', 1;

    IF @FromAccountId = @ToAccountId
        THROW 50002, 'Source and destination accounts cannot be the same.', 1;

    BEGIN TRANSACTION;

    BEGIN TRY
        -- Debit
        UPDATE Accounts
        SET Balance = Balance - @Amount
        WHERE AccountId = @FromAccountId AND Balance >= @Amount;

        IF @@ROWCOUNT = 0
            THROW 50003, 'Insufficient funds or account not found.', 1;

        -- Credit
        UPDATE Accounts
        SET Balance = Balance + @Amount
        WHERE AccountId = @ToAccountId;

        IF @@ROWCOUNT = 0
            THROW 50004, 'Destination account not found.', 1;

        -- Log the transfer
        INSERT INTO TransferLog (FromAccountId, ToAccountId, Amount, TransferDate)
        VALUES (@FromAccountId, @ToAccountId, @Amount, GETDATE());

        COMMIT TRANSACTION;

    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;

        -- Re-throw the error with context
        DECLARE @ErrorMessage NVARCHAR(4000) = ERROR_MESSAGE();
        DECLARE @ErrorSeverity INT = ERROR_SEVERITY();
        DECLARE @ErrorState INT = ERROR_STATE();

        RAISERROR(@ErrorMessage, @ErrorSeverity, @ErrorState);
        -- Or in SQL Server 2012+:
        -- THROW;
    END CATCH;
END;
GO

Error functions inside CATCH:

BEGIN CATCH
    SELECT
        ERROR_NUMBER()    AS ErrorNumber,    -- The error code (e.g., 50003)
        ERROR_SEVERITY()  AS ErrorSeverity,  -- 1-25 (16 = general user errors)
        ERROR_STATE()     AS ErrorState,     -- State within the error (for Microsoft support)
        ERROR_PROCEDURE() AS ErrorProcedure, -- Which stored procedure threw the error
        ERROR_LINE()      AS ErrorLine,      -- Line number where the error occurred
        ERROR_MESSAGE()   AS ErrorMessage;   -- The human-readable message
END CATCH;

Stored Procedures with Table-Valued Parameters

When you need to pass a list of values into a stored procedure:

-- Step 1: Create a user-defined table type
CREATE TYPE OrderIdList AS TABLE
(
    OrderId INT NOT NULL
);
GO

-- Step 2: Use it in a stored procedure
CREATE PROCEDURE sp_BulkCancelOrders
    @OrderIds OrderIdList READONLY -- READONLY is required for TVP parameters
AS
BEGIN
    SET NOCOUNT ON;

    UPDATE o
    SET o.Status = 'Cancelled'
    FROM Orders o
    JOIN @OrderIds ids ON o.OrderId = ids.OrderId
    WHERE o.Status = 'Pending';

    SELECT @@ROWCOUNT AS CancelledCount;
END;
GO

-- Calling from T-SQL
DECLARE @Ids OrderIdList;
INSERT INTO @Ids VALUES (101), (102), (103), (104);

EXEC sp_BulkCancelOrders @OrderIds = @Ids;

// Calling from C# with ADO.NET
var dt = new DataTable();
dt.Columns.Add("OrderId", typeof(int));
dt.Rows.Add(101);
dt.Rows.Add(102);
dt.Rows.Add(103);

using var connection = new SqlConnection(connectionString);
await connection.OpenAsync();

using var command = new SqlCommand("sp_BulkCancelOrders", connection);
command.CommandType = CommandType.StoredProcedure;

var param = command.Parameters.AddWithValue("@OrderIds", dt);
param.SqlDbType = SqlDbType.Structured;
param.TypeName = "OrderIdList"; // Must match the user-defined table type name

await command.ExecuteNonQueryAsync();

Parameter Sniffing — The Hidden Performance Problem

When a stored procedure is first executed, SQL Server compiles it and caches the execution plan based on the parameter values used in that first call. If the first call uses unusual values, the cached plan may be terrible for subsequent typical calls.

-- First call: CustomerId = 1 (a VIP with 50,000 orders — table scan is fine)
-- SQL Server caches a plan with a table scan
EXEC sp_GetOrdersByCustomer @CustomerId = 1;

-- All subsequent calls use the same table scan plan
-- Even for CustomerId = 99999 (a new customer with 2 orders — should use an index seek)
EXEC sp_GetOrdersByCustomer @CustomerId = 99999; -- Slow! Wrong plan.

Solutions:

-- Option 1: OPTION (RECOMPILE) — recompile every execution (eliminates sniffing, adds CPU)
CREATE PROCEDURE sp_GetOrdersByCustomer
    @CustomerId INT
AS
BEGIN
    SELECT * FROM Orders WHERE CustomerId = @CustomerId
    OPTION (RECOMPILE);
END;

-- Option 2: Local variables — sniff the parameter into a local variable
-- The optimizer sees a local variable with unknown value and uses a generic plan
CREATE PROCEDURE sp_GetOrdersByCustomer
    @CustomerId INT
AS
BEGIN
    DECLARE @LocalCustomerId INT = @CustomerId; -- Optimizer cannot sniff the local variable
    SELECT * FROM Orders WHERE CustomerId = @LocalCustomerId;
END;

-- Option 3: WITH RECOMPILE on the procedure — recompile entire procedure each time
CREATE PROCEDURE sp_GetOrdersByCustomer
    @CustomerId INT
WITH RECOMPILE
AS
BEGIN
    SELECT * FROM Orders WHERE CustomerId = @CustomerId;
END;

-- Option 4: Optimize for a specific value or unknown
SELECT * FROM Orders WHERE CustomerId = @CustomerId
OPTION (OPTIMIZE FOR (@CustomerId = 42));     -- Optimize for a specific typical value
OPTION (OPTIMIZE FOR (@CustomerId UNKNOWN));  -- Optimize based on average statistics

Stored Procedure vs View vs Function

-- VIEW — a stored SELECT query, treated like a table
-- Cannot take parameters, cannot perform DML (usually), no execution plan caching benefit
CREATE VIEW vw_ActiveOrders AS
SELECT OrderId, CustomerId, TotalAmount
FROM Orders WHERE Status = 'Active';

SELECT * FROM vw_ActiveOrders WHERE CustomerId = 42;

-- SCALAR FUNCTION — returns a single value, can be used inline in SELECT
-- WARNING: scalar functions called per-row in a query execute row-by-row
-- They can devastate query performance on large result sets
CREATE FUNCTION fn_GetCustomerTotalSpend(@CustomerId INT)
RETURNS DECIMAL(18, 2)
AS
BEGIN
    RETURN (SELECT SUM(TotalAmount) FROM Orders WHERE CustomerId = @CustomerId);
END;

-- This runs fn_GetCustomerTotalSpend once for EVERY row in Customers
-- 100,000 customers = 100,000 function calls = very slow
SELECT CustomerId, dbo.fn_GetCustomerTotalSpend(CustomerId) AS TotalSpend
FROM Customers; -- AVOID scalar UDFs in SELECT lists on large tables

-- TABLE-VALUED FUNCTION (INLINE) — returns a table, optimizer can merge it into the query plan
-- Much better performance than scalar UDFs
CREATE FUNCTION fn_GetCustomerOrders(@CustomerId INT, @StartDate DATE)
RETURNS TABLE
AS
RETURN
(
    SELECT OrderId, OrderDate, TotalAmount
    FROM Orders
    WHERE CustomerId = @CustomerId AND OrderDate >= @StartDate
);

SELECT * FROM dbo.fn_GetCustomerOrders(42, '2024-01-01');

-- STORED PROCEDURE — can do everything: DML, transactions, output parameters, error handling
-- Cannot be used inline in SELECT like functions
-- Cannot be used in views or other functions

5. Interview Questions and Answers

Indexes

Q: What is the difference between a clustered and a nonclustered index?

A clustered index determines the physical storage order of data in the table. The leaf nodes of the clustered index B-Tree are the actual data rows. There can be only one clustered index per table because data can only be physically sorted one way. A nonclustered index is a separate B-Tree structure. Its leaf nodes contain the indexed column values and a row locator (the clustered index key or a physical pointer to the heap row). A table can have up to 999 nonclustered indexes.

Q: What is a covering index?

A covering index is a nonclustered index that includes all the columns needed to satisfy a query — both the filter columns (key columns) and the columns in the SELECT list (added via INCLUDE). When a query is covered by an index, SQL Server can answer it entirely from the index without doing a Key Lookup back to the main table. This eliminates the most expensive part of nonclustered index usage for queries that return many rows.

Q: What is index fragmentation and how do you fix it?

Fragmentation occurs as rows are inserted, updated, and deleted over time. Index pages become out of order or partially empty, causing SQL Server to read more pages than necessary for range scans. Under 30% fragmentation, use ALTER INDEX ... REORGANIZE — it is an online, low-impact operation that compacts and reorders pages. Over 30% fragmentation, use ALTER INDEX ... REBUILD — it recreates the index from scratch, resets fragmentation to near zero, and updates statistics. Rebuild is more disruptive but more thorough.

Q: Why can a table have only one clustered index?

Because a clustered index determines the physical order of rows on disk. Data can only be sorted one way. When you define a clustered index on a column, the actual data pages are rearranged to match that sort order. You cannot simultaneously have the rows sorted by OrderDate and by CustomerId — you have to choose one physical arrangement.

Q: What is a filtered index and when would you use one?

A filtered index covers only a subset of rows, defined by a WHERE clause in the index definition. Use it when your queries consistently filter on a specific condition and that condition selects a small fraction of rows — for example, an index on Status only for Status = 'Active' on an orders table where 95% of orders are archived. The index is smaller, faster to maintain, and faster to search than a full index.

DELETE, DROP, TRUNCATE

Q: What is the difference between DELETE and TRUNCATE?

DELETE removes rows one at a time and logs every deleted row in the transaction log. It fires DELETE triggers. It respects foreign key constraints. It does not reset the identity counter. It can include a WHERE clause to delete specific rows. TRUNCATE removes all rows by deallocating data pages with minimal logging. It does not fire triggers. It is blocked by foreign key constraints. It resets the identity counter to the seed value. It is much faster for large tables. Both are transactional and can be rolled back within an explicit transaction.

Q: Why can TRUNCATE fail when DELETE works?

TRUNCATE fails if the table is referenced by a foreign key constraint in another table, even if the referencing table is empty. This is because TRUNCATE operates at the page level and SQL Server does not check for referencing rows during a page deallocation. DELETE checks foreign key constraints row by row, so it works correctly (and fails with a constraint violation if referencing rows exist). To truncate a table with foreign key references, you must disable or drop the foreign keys first.

Q: Can you roll back a TRUNCATE or DROP statement?

Yes, if the statement is inside an explicit transaction. Both TRUNCATE and DROP are logged operations. If you execute them inside a BEGIN TRANSACTION block and then call ROLLBACK, the operation is undone. Outside of an explicit transaction, both operations are committed immediately and cannot be undone through normal SQL means.

SQL Optimization

Q: What is a SARGable predicate?

A SARGable (Search ARGument able) predicate is a WHERE condition that SQL Server can use an index seek to evaluate. The indexed column must appear alone on one side of the comparison. Wrapping the column in a function (YEAR(OrderDate), UPPER(Name), LEFT(Code, 3)), applying arithmetic to it, or comparing it to a value of a different data type (implicit conversion) makes the predicate non-SARGable — SQL Server must evaluate it for every row with a full table scan. The fix is to rewrite the condition so the transformation is applied to the value, not the column.

Q: What is parameter sniffing?

Parameter sniffing occurs when SQL Server compiles a stored procedure and caches the execution plan based on the parameter values used in the very first execution. If the first execution uses atypical values (a customer with 50,000 orders when most customers have 5), the cached plan is optimised for that unusual case and performs poorly for typical executions. Solutions include OPTION (RECOMPILE) to recompile on every execution, using local variables to prevent the optimizer from seeing the parameter value, or OPTIMIZE FOR UNKNOWN to base the plan on average statistics.

Q: What is the difference between a table scan and an index seek?

A table scan (or clustered index scan) reads every data page in the table from start to finish. The cost is proportional to the table size. An index seek traverses the B-Tree of an index to locate exactly the rows that match the predicate. The cost is proportional to the logarithm of the index size — effectively constant for most practical purposes. For a table with ten million rows, a table scan reads millions of rows. An index seek reads perhaps 30 pages.

Q: When would a full table scan be faster than an index seek?

When the query needs to return a large percentage of the rows. Reading an index and then doing Key Lookups to fetch the actual row data involves two reads per row. If you need 80% of the rows, it is faster to just read the table sequentially. The SQL Server optimizer uses statistics to estimate how many rows a predicate will return and chooses accordingly. The tipping point is typically somewhere between 5% and 30% of rows, depending on the data distribution.

Stored Procedures

Q: What is SET NOCOUNT ON and why do you use it?

By default, SQL Server sends a message for every statement that affects rows (the “N rows affected” message). In a stored procedure with many statements, these messages add up to unnecessary network traffic and interfere with some client applications that check for row counts. SET NOCOUNT ON suppresses these messages. It is standard practice to include it at the top of every stored procedure.

Q: What is the difference between RAISERROR and THROW?

Both signal an error condition. THROW (SQL Server 2012+) is simpler — it re-raises the current exception in a CATCH block with the original error number and preserves the stack trace. RAISERROR is the older syntax, more flexible (can format messages with arguments), but re-raised errors get a new error number. In modern SQL Server, prefer THROW for re-raising caught exceptions, and THROW with an error number for raising new errors.

Q: What is SCOPE_IDENTITY() and how is it different from @@IDENTITY?

Both return the last identity value generated. @@IDENTITY returns the last identity generated in the current session, regardless of scope — including values generated by triggers. SCOPE_IDENTITY() returns the last identity generated in the current scope (the current stored procedure or batch), excluding identity values generated by triggers. Always use SCOPE_IDENTITY() in stored procedures. Using @@IDENTITY after an INSERT can return an unexpected value if the table has a trigger that also inserts into a table with an identity column.

Q: Why should you avoid the sp_ prefix for user stored procedures?

SQL Server resolves sp_ procedures by checking the master database first, then the current database. This means every call to your sp_YourProcedure pays the overhead of a failed lookup in the master database before finding the correct procedure in your database. Additionally, if Microsoft ever creates a system procedure with the same name, it will silently take precedence over yours. Use usp_ or a schema-based naming convention instead.

Optimization Quick Checks

Slow query?
    1. Run with actual execution plan (Ctrl+M in SSMS)
    2. Look for Table Scan / Clustered Index Scan on large tables
    3. Look for Key Lookup — consider INCLUDE columns
    4. Check for implicit type conversions (yellow triangles)
    5. Check SET STATISTICS IO ON — high logical reads = missing index
