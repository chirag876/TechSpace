Clean Architecture

Basic Level

Q1: What is Clean Architecture?
A: Clean Architecture is a design pattern that emphasizes separation of concerns and independence of frameworks. It organizes code into layers (Presentation, Application, Domain, Infrastructure) where each layer has a specific responsibility and minimal dependencies on other layers.

Q2: What are the main layers in Clean Architecture?
A:

  • Presentation Layer: UI/API controllers, view models
  • Application Layer: Business logic, use cases, DTOs, specifications
  • Domain Layer: Entities, value objects, interfaces, domain services
  • Infrastructure Layer: Database access, external services, implementations

Q3: What is the Dependency Inversion Principle in Clean Architecture?
A: High-level modules should not depend on low-level modules. Both should depend on abstractions. This is achieved through interfaces and dependency injection, making code loosely coupled and testable.

Q4: Can you explain the flow of data in Clean Architecture?
A: Data typically flows from the Presentation Layer → Application Layer (services) → Domain Layer (business logic) → Infrastructure Layer (data access). The reverse flow uses interfaces to maintain dependency direction.

Intermediate Level

Q5: What are DTOs and why are they used in Clean Architecture?
A: Data Transfer Objects are objects used to transfer data between layers. They prevent exposing domain models directly to clients, providing a contract for API responses and decoupling presentation from domain logic.

Q6: How do you handle database queries in Clean Architecture? (Specification Pattern)
A: The Specification Pattern encapsulates query logic into separate classes. Instead of writing queries directly in repositories, you create Specification objects that contain the criteria and are passed to repositories, improving reusability and testability.

Q7: What is the Repository Pattern and how does it fit in Clean Architecture?
A: The Repository Pattern abstracts data access logic. It acts as an in-memory collection of domain objects, sitting in the Infrastructure Layer but exposing interfaces defined in the Application/Domain layers, enabling easy testing and switching data sources.

Q8: How do you handle cross-cutting concerns (logging, caching, validation) in Clean Architecture?
A: Cross-cutting concerns should be handled through:

  • Middleware (in ASP.NET Core)
  • Decorators (wrapping service implementations)
  • Aspects (using libraries like PostSharp)
  • Pipeline behaviors (MediatR)

Q9: What’s the difference between a Use Case and a Service in Clean Architecture?
A: A Use Case (Application Service) represents a single business operation that can be performed by the application. A Service may be a utility or domain service. Use Cases are orchestrators; services contain reusable business logic.

Advanced Level

Q10: How do you implement Domain-Driven Design (DDD) within Clean Architecture?
A: Combine them by:

  • Using Aggregates as domain models (clusters of entities)
  • Defining Bounded Contexts matching business domains
  • Using Value Objects for immutable domain concepts
  • Placing Domain Services in the Domain layer for cross-aggregate logic
  • Creating Ubiquitous Language shared between developers and business

Q11: How do you handle circular dependencies in Clean Architecture?
A:

  • Move common abstractions to a separate layer
  • Use dependency inversion (depend on abstractions)
  • Refactor domain logic into separate, focused services
  • Consider if architectural boundaries are correctly defined
  • Use interfaces to break dependency cycles

Q12: Explain the CQRS pattern and how it integrates with Clean Architecture.
A: Command Query Responsibility Segregation separates read and write operations. In Clean Architecture:

  • Commands handle write operations (use cases that modify state)
  • Queries handle read operations (optimized for retrieval)
  • Each can have its own data model and optimization strategies
  • Improves scalability and makes intent clear

Q13: How would you structure a multi-tenant Clean Architecture application?
A:

  • Add Tenant Context handling in middleware/application service
  • Isolate tenant-specific business logic in application layer
  • Use tenant-aware repositories in infrastructure layer
  • Consider database design: shared DB with tenant column, or separate databases per tenant
  • Validate tenant access at application boundaries

Q14: What are the common mistakes in implementing Clean Architecture and how do you avoid them?
A:

  • Over-engineering: Don’t create layers for simple applications
  • Leaky abstractions: Ensure layers truly encapsulate responsibilities
  • Wrong dependency direction: Always depend inward, never outward
  • God objects: Keep entities and services focused
  • Missing domain logic: Don’t just use the domain layer for data storage
  • Over-abstraction: Don’t create interfaces for everything

Singleton & Sealed Classes

Basic Level

Q15: What is a Singleton pattern?
A: Singleton is a creational design pattern that ensures a class has only one instance and provides a global point of access to it. It’s useful for resources that should be shared application-wide (logger, database connection pool, configuration).

Q16: How do you implement a Singleton in C#?
A:

// Lazy initialization
public sealed class Singleton
{
    private static readonly Lazy<Singleton> _instance = 
        new Lazy<Singleton>(() => new Singleton());
    
    public static Singleton Instance => _instance.Value;
    private Singleton() { }
}

Q17: What is a sealed class?
A: A sealed class cannot be inherited. It’s declared using the sealed modifier. It’s useful for preventing unintended inheritance and enabling compiler optimizations since the compiler knows no derived classes exist.

Q18: Can you create an instance of a sealed class?
A: Yes, you can create instances of sealed classes. The sealed modifier only prevents inheritance. You still instantiate them normally.

Q19: Can a sealed class have a sealed method?
A: No, it’s redundant. All methods in a sealed class are already implicitly sealed since the class cannot be inherited. The sealed keyword on methods only makes sense in derived classes overriding virtual members.

Intermediate Level

Q20: What are the different ways to implement Singleton in C#? (Compare them)
A:

// 1. Eager initialization
public sealed class SingletonEager
{
    private static readonly SingletonEager _instance = new SingletonEager();
    private SingletonEager() { }
    public static SingletonEager Instance => _instance;
}

// 2. Lazy initialization (thread-safe)
public sealed class SingletonLazy
{
    private static readonly Lazy<SingletonLazy> _instance = 
        new Lazy<SingletonLazy>(() => new SingletonLazy());
    private SingletonLazy() { }
    public static SingletonLazy Instance => _instance.Value;
}

// 3. Double-checked locking (not recommended in .NET)
public sealed class SingletonDoubleCheck
{
    private static SingletonDoubleCheck _instance;
    private static readonly object _lock = new object();
    
    private SingletonDoubleCheck() { }
    
    public static SingletonDoubleCheck Instance
    {
        get
        {
            if (_instance == null)
            {
                lock (_lock)
                {
                    if (_instance == null)
                        _instance = new SingletonDoubleCheck();
                }
            }
            return _instance;
        }
    }
}

Best practice: Use Lazy<T> for the cleanest, thread-safe implementation.

Q21: Is Singleton thread-safe? How?
A: With proper implementation (like Lazy<T>), yes. Lazy<T> uses LazyThreadSafetyMode.ExecutionAndPublication by default, ensuring thread-safe lazy initialization. The private constructor prevents external instantiation.

Q22: What are the problems with Singleton pattern?
A:

  • Hard to test: Singletons with global state make unit testing difficult
  • Hidden dependencies: Classes depend on a global instance, making dependencies unclear
  • Concurrency issues: If not implemented carefully, can have threading problems
  • Violates Single Responsibility: Manages its own lifecycle + business logic
  • Makes code tightly coupled: Difficult to swap implementations
  • Not suitable for multi-threaded environments if poorly designed

Q23: Can you use Dependency Injection instead of Singleton?
A: Yes, and it’s preferred in modern .NET applications. Use DI containers to register services:

// Register as singleton
services.AddSingleton<IMyService, MyService>();

// Inject where needed
public class MyController
{
    private readonly IMyService _service;
    public MyController(IMyService service) => _service = service;
}

This is cleaner, more testable, and follows SOLID principles.

Q24: When should you use a sealed class?
A:

  • When class is designed to not be inherited
  • When you want to prevent accidental misuse
  • For performance: sealed classes allow virtual method calls to be devirtualized
  • When you control the entire hierarchy and want to prevent future inheritance
  • Example: String is sealed in .NET

Advanced Level

Q25: Explain sealed methods in the context of virtual method overriding.
A:

public class Base
{
    public virtual void DoSomething() { }
}

public class Derived : Base
{
    public sealed override void DoSomething() { }
    // Prevents further overriding in subclasses
}

public class FurtherDerived : Derived
{
    // Cannot override DoSomething() here - it's sealed
}

Sealed methods prevent derived classes from overriding them, useful for security or behavior guarantees.

Q26: What’s the relationship between Singleton and sealed classes? (Commonly ignored)
A: They’re independent concepts:

  • Sealed class: Prevents inheritance (structural constraint)
  • Singleton: Ensures one instance (behavioral pattern)
    A Singleton should often be sealed to prevent inheritance and instantiation workarounds, but you can have sealed non-Singletons and Singletons that aren’t sealed (though not recommended).

Q27: How does reflection affect Singleton pattern?
A:

// Reflection can break Singleton!
var constructor = typeof(Singleton).GetConstructors(
    System.Reflection.BindingFlags.NonPublic | 
    System.Reflection.BindingFlags.Instance)[0];
var instance = (Singleton)Activator.CreateInstance(
    typeof(Singleton), true);
// Now you have a second instance!

Defense: Use sealed class, make constructor sealed, or throw exception in constructor if IsValueCreated is true.

Q28: Explain the difference between Singleton and Static Classes.
A:

Aspect Singleton Static Class
Instance One instance created No instances
Can implement interfaces Yes No
Can inherit Yes (if not sealed) No (always abstract)
Can be passed as parameter Yes No
Serialization Possible with care Not applicable
Testability Better (can mock interface) Harder to test

Static classes are for utility functions; Singletons for stateful, reusable instances.

Q29: How do you handle Singleton serialization and deserialization?
A:

[Serializable]
public sealed class Singleton
{
    private static readonly Lazy<Singleton> _instance = 
        new Lazy<Singleton>(() => new Singleton());
    
    public static Singleton Instance => _instance.Value;
    
    private Singleton() { }
    
    // Ensure deserialization returns the same instance
    [OnDeserialized]
    private void OnDeserialized(StreamingContext context) { }
    
    private object ReadResolve()
    {
        return Instance; // Return the existing singleton instance
    }
}

ASP.NET Core Lifecycle

Basic Level

Q30: What are the main phases in ASP.NET Core request lifecycle?
A:

  1. Request arrives at server
  2. Middleware pipeline processes request (in order)
  3. Routing determines which handler processes request
  4. Action/handler executes (MVC, Razor Pages, gRPC, etc.)
  5. Response flows back through middleware (in reverse order)
  6. Response sent to client

Q31: What is the Startup class in ASP.NET Core?
A: The Startup class (or Program.cs in .NET 6+) configures:

  • ConfigureServices(): Registers services in the dependency injection container
  • Configure(): Configures the HTTP request pipeline with middleware

In .NET 6+, this is simplified using the Minimal Hosting Model in Program.cs.

Q32: What are middleware components?
A: Middleware are components that handle HTTP requests and responses. They form a pipeline where each middleware can process the request, pass it to the next middleware, and process the response coming back. Examples: Authentication, Logging, Error handling, CORS.

Q33: What is the order of middleware execution?
A: Middleware executes in the order it’s registered in the Configure() method for the request phase, then in reverse order for the response phase (like a stack).

Q34: What is dependency injection in ASP.NET Core?
A: Dependency Injection is a technique where a class doesn’t create its dependencies but receives them (usually through constructor). ASP.NET Core has a built-in DI container that manages object lifetimes and instantiation.

Q35: What are the different service lifetimes in ASP.NET Core?
A:

  • Transient: New instance created every time (stateless services)
  • Scoped: New instance per HTTP request (DbContext, repositories)
  • Singleton: Same instance for the entire application lifetime (configuration, logging)

Intermediate Level

Q36: Explain the difference between Configure and ConfigureServices.
A:

  • ConfigureServices(): Registers services in DI container. Called first. Happens once at startup.
  • Configure(): Sets up request pipeline. Called once at startup. Receives services from DI container. Called for each request to process it through middleware.

Q37: What is IApplicationBuilder and IServiceCollection?
A:

  • IServiceCollection: Used in ConfigureServices() to register services
  • IApplicationBuilder: Used in Configure() to build the request pipeline with middleware

Q38: How does routing work in ASP.NET Core?
A: Routing matches incoming HTTP requests to handlers (controller actions, Razor Pages, etc.) based on:

  • Conventional routing: Pattern like {controller}/{action}/{id}
  • Attribute routing: [Route("api/[controller]")] directly on controller/action
  • Endpoint routing (.NET Core 3+): More flexible, uses MapControllers(), MapRazorPages(), etc.

Q39: What is the difference between UseRouting() and UseEndpoints()?
A:

  • UseRouting(): Determines which endpoint should handle the request
  • UseEndpoints(): Executes the selected endpoint
  • Middleware between them can access route data via HttpContext.GetRouteData()

Q40: How do you handle exceptions in ASP.NET Core?
A:

  • Try-catch blocks in action methods
  • Exception filter: [ExceptionFilter]
  • Global exception handling middleware:
app.UseExceptionHandler(app => 
{
    app.Run(async context =>
    {
        var feature = context.Features.Get<IExceptionHandlerFeature>();
        // Handle exception
    });
});
  • Problem details middleware (.NET 7+)

Q41: What is the role of IHostBuilder in ASP.NET Core?
A: IHostBuilder is used to configure and build the host that runs an ASP.NET Core application. It configures:

  • Services (DI container)
  • Configuration (appsettings.json, environment variables)
  • Logging
  • Built-in middleware

Q42: Explain service resolution in the DI container.
A: When a service is requested:

  1. Container checks if the service is registered
  2. Checks the lifetime (Transient, Scoped, Singleton)
  3. Creates/retrieves the instance
  4. Recursively resolves constructor dependencies
  5. Returns the configured instance

Advanced Level

Q43: What is the difference between IServiceCollection and IServiceProvider?
A:

  • IServiceCollection: Used at startup to register services (container configuration)
  • IServiceProvider: Used at runtime to resolve/retrieve registered services (container query)
// ConfigureServices
services.AddScoped<IRepository, Repository>(); // IServiceCollection

// In action/middleware
var repo = serviceProvider.GetRequiredService<IRepository>(); // IServiceProvider

Q44: How does scope work in ASP.NET Core dependency injection? (Commonly ignored)
A: Each HTTP request creates a new IServiceScope:

// Correct: Use scoped services with HttpContext
public async Task InvokeAsync(HttpContext context, IMyService service)
{
    // 'service' is scoped to this request
}

// Wrong: Capturing scoped service in static/singleton
public static IMyService _service; // Danger!
services.AddSingleton<IMyService>(_ => _service); // Scoped in singleton!

Scoped services must never be captured in singletons or statics.

Q45: What is the difference between AddScoped vs AddSingleton when registering DbContext?
A:

  • AddDbContext(): Automatically registers as Scoped (default). Safe because DbContext is not thread-safe.
  • AddSingleton(): Dangerous! DbContext is not thread-safe for concurrent requests.

Q46: Explain the host lifecycle in ASP.NET Core.
A:

1. CreateHostBuilder() - Creates IHostBuilder
2. Build() - Creates IHost
3. StartAsync() - Calls all IHostedService.StartAsync()
4. Request handling loop - Main application logic
5. StopAsync() - Calls all IHostedService.StopAsync() in reverse
6. Dispose() - Cleans up resources

Q47: What are IHostedService and BackgroundService?
A:

  • IHostedService: Interface for long-running background tasks in application lifetime
  • BackgroundService: Base class that implements IHostedService, providing ExecuteAsync() override
public class TimerService : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            // Long-running task
            await Task.Delay(1000, stoppingToken);
        }
    }
}

Q48: How does middleware ordering affect application behavior? (Commonly ignored)
A: Order is critical:

app.UseExceptionHandler(); // Should be first to catch exceptions from other middleware
app.UseAuthentication();   // Before authorization
app.UseAuthorization();    // After authentication
app.UseRouting();          // Determine endpoint
app.MapControllers();      // Register endpoints
app.UseEndpoints(...);     // Execute endpoint

Wrong order = bugs that are hard to track (e.g., authorization before authentication).

Q49: Explain middleware short-circuit behavior.
A: Middleware can stop the pipeline without calling next():

app.Use(async (context, next) =>
{
    if (someCondition)
    {
        context.Response.StatusCode = 401; // Short-circuit
        return; // Don't call next()
    }
    await next(); // Continue pipeline
});

Useful for: authentication failures, rate limiting, request validation.

Q50: What is the purpose of the health check middleware?
A: Health checks provide endpoints to determine application readiness/liveness for orchestration systems (Kubernetes, load balancers):

services.AddHealthChecks()
    .AddDbContextCheck<AppDbContext>();

app.MapHealthChecks("/health");

.NET Core vs .NET Framework

Basic Level

Q51: What is .NET Framework?
A: .NET Framework is the original Microsoft .NET platform (released 2002) running on Windows only. It’s the full framework with deep Windows integration, large runtime, and extensive built-in libraries. It’s now in maintenance mode.

Q52: What is .NET Core?
A: .NET Core is the modern, cross-platform, open-source rewrite of .NET Framework (released 2016). Starting from .NET 5, it’s just called “.NET” and is the future direction. It runs on Windows, Linux, and macOS.

Q53: Is .NET Core open-source?
A: Yes, .NET Core/.NET is completely open-source on GitHub under MIT license. Contributions welcome.

Q54: Can .NET Framework applications run on .NET Core?
A: Not directly, but you can migrate them. .NET Framework and .NET Core are incompatible by design. However, .NET Framework code can often run on .NET Core with modifications (remove Windows-specific code, use compatible NuGet packages).

Q55: What is the release cadence for .NET Core?
A:

  • .NET releases annually (March) with LTS versions every 2 years
  • Current LTS versions: .NET 6, 8
  • Non-LTS versions: 5, 7, 9 (supported for 18 months)
  • LTS versions get 3 years of support

Intermediate Level

Q56: Compare CLR (Common Language Runtime) in .NET Framework vs .NET Core.
A:

Aspect .NET Framework CLR .NET Core CLR
Platform Windows only Cross-platform
Size Large (~200MB) Smaller, modular
Performance Good Better (optimized)
Startup Slower Faster
Deployment GAC (Global Assembly Cache) Self-contained
Updates OS patches App updates independently

Q57: What is the difference between Windows Presentation Foundation (WPF) and ASP.NET Core?
A:

  • WPF: Desktop UI framework for .NET Framework (Windows only)
  • ASP.NET Core: Web framework, cross-platform
  • .NET has WPF/WinForms for Windows desktop, Maui for cross-platform mobile/desktop, Blazor for web UIs

Q58: How do you migrate from .NET Framework to .NET Core?
A:

  1. Use Portability Analyzer to check compatibility
  2. Identify Windows-specific code (System.Windows, etc.)
  3. Find alternative NuGet packages compatible with .NET
  4. Update project file to target .NET (csproj format)
  5. Fix API calls (some removed, some changed)
  6. Test thoroughly
  7. Consider containerization for deployment

Q59: What’s the difference in how assemblies are deployed?
A:

Aspect .NET Framework .NET Core
Assembly resolution GAC, application bin folder App-local only
Version conflicts GAC bindings Single version per app
Deployment xcopy to bin folder Self-contained or runtime-dependent
Side-by-side versions Framework versions on machine Per-application

Q60: What is SelfContained deployment in .NET Core? (Commonly ignored)
A: Self-contained deployment bundles the entire .NET runtime with your application:

dotnet publish -c Release --self-contained -r win-x64
  • Advantages: Works without .NET installed, versions isolated
  • Disadvantages: Larger deployment size, security patches must be applied per app
  • Opposed to: Framework-dependent deployment (smaller, uses machine .NET runtime)

Advanced Level

Q61: Explain the architecture differences in how types are loaded in .NET Framework vs .NET Core.
A:

  • .NET Framework: Single CLR per AppDomain, types loaded into AppDomain
  • .NET Core: No AppDomains, types loaded into single shared runtime
  • .NET Core implication: No isolation between assemblies; if one loads v1.0, all see v1.0

Q62: How do you handle breaking changes when migrating from .NET Framework to .NET Core?
A:

  • Removed namespaces: System.Web, System.Net.Mail (web-specific)
  • API changes: Some collection methods signature changes
  • Platform APIs: P/Invoke for Windows APIs still works, but other platform code removed
  • Solution: Use compatibility shims, create abstraction layers, test against .NET

Q63: What is the difference in how NuGet packages target different frameworks?
A:

<!-- Legacy .NET Framework -->
<Target Framework="net462" />

<!-- Modern .NET -->
<Target Framework="net8.0" />

<!-- Multi-targeting -->
<TargetFrameworks>net462;net8.0</TargetFrameworks>

.NET Core packages can target .NET Framework with compatibility layer, but not vice versa.

Q64: Explain the concept of .NET Standard and why it existed.
A: .NET Standard is a specification of .NET APIs that multiple .NET implementations must support:

  • Purpose: Allow libraries to target one framework (.NET Standard 2.0) and work on both .NET Framework and .NET Core
  • History: Needed when .NET Core was incompatible with Framework
  • Modern status: No longer necessary since .NET Core is universal. Target .NET directly.
// Old: library targets .NET Standard for compatibility
<TargetFramework>netstandard2.0</TargetFramework>

// Modern: target .NET directly
<TargetFramework>net8.0</TargetFramework>

Q65: How do licensing and support differ between .NET Framework and .NET Core?
A:

  • .NET Framework: Licensed per OS copy, mainstream support ended 2020, extended support until 2029
  • .NET Core/.NET: MIT open-source license, community and Microsoft support, LTS versions get 3-year support
  • Cost: .NET is free (open-source); Framework licensing depends on Windows licensing

Q66: What is the performance difference between .NET Framework and .NET Core? (Commonly ignored)
A: .NET Core is generally faster:

  • Startup time: .NET Core ~10ms vs Framework ~100ms+
  • Throughput: .NET Core 30-40% faster in benchmarks (TechEmpower)
  • Memory: .NET Core more efficient (no startup overhead)
  • Reasons: Redesigned for cloud/containers, better JIT compilation, AOT compilation support
  • Benchmarks: Use BenchmarkDotNet to measure in your code

Q67: Explain how the .NET ecosystem converged (from multiple runtimes to unified .NET).
A:

  • Before .NET 5: Separate runtimes (.NET Framework, .NET Core, Mono)
  • .NET 5+: All merged into one unified platform
  • Runtimes available: CoreCLR (JIT), Mono (ahead-of-time for mobile), NativeAOT
  • Platform support: Windows, Linux, macOS, iOS, Android, WebAssembly
  • Result: Single target (.NET 8, 9, etc.) that works everywhere

Microservices Communication

Basic Level

Q68: What is a microservice architecture?
A: Microservices architecture breaks an application into small, independently deployable services, each handling a specific business capability. They communicate through well-defined APIs (REST, gRPC, messaging), are loosely coupled, and can scale independently.

Q69: What are the main communication patterns between microservices?
A:

  • Synchronous (blocking): REST, gRPC (wait for response)
  • Asynchronous (non-blocking): Message queues, event streaming (fire and forget)
  • Request-Reply: Service calls and waits for response (RESTful)
  • Publish-Subscribe: Services publish events, others subscribe

Q70: What is REST API communication?
A: REST (Representational State Transfer) uses HTTP verbs (GET, POST, PUT, DELETE) to operate on resources:

// GET: Retrieve
GET /api/products/1

// POST: Create
POST /api/products
Body: { "name": "Product", "price": 100 }

// PUT: Update
PUT /api/products/1
Body: { "name": "Updated", "price": 200 }

// DELETE: Remove
DELETE /api/products/1

Q71: What is gRPC communication?
A: gRPC is a high-performance RPC framework using HTTP/2 and Protocol Buffers:

  • Binary protocol: More efficient than JSON
  • Streaming: Supports bidirectional streaming
  • Performance: Faster than REST
  • Drawback: Requires .proto contract definition, not browser-friendly

Q72: What is message-based communication?
A: Services communicate through message queues (RabbitMQ, Azure Service Bus) or event streams (Kafka):

  • Decoupled: Services don’t need to know each other
  • Asynchronous: Sender doesn’t wait for processing
  • Reliable: Message persisted until consumed
  • Scalable: Multiple consumers can process messages

Q73: What’s the difference between synchronous and asynchronous communication?
A:

Aspect Synchronous (REST) Asynchronous (Messaging)
Blocking Yes, waits for response No, returns immediately
Coupling Tightly coupled Loosely coupled
Error handling Immediate response codes Retry mechanisms
Latency Higher (network wait) Lower (return immediately)
Use case Real-time updates High-volume operations

Intermediate Level

Q74: How do you handle API versioning in microservices?
A:

// URL versioning
GET /api/v1/products
GET /api/v2/products

// Header versioning
GET /api/products
Header: X-API-Version: 2

// Query parameter
GET /api/products?version=2

// Accept header
GET /api/products
Header: Accept: application/vnd.myapi.v2+json

Recommendation: URL versioning is simplest; header versioning more RESTful.

Q75: What is service discovery and why is it important?
A: Service discovery is the process of finding which service instances are available (IP, port):

  • Manual: Hardcoded service URLs (not scalable)
  • Client-side: Client queries registry (Consul, Eureka)
  • Server-side: Load balancer queries registry
  • Cloud-native: Kubernetes handles service discovery automatically
  • Importance: Services are dynamic; instances appear/disappear during scaling

Q76: How do you implement retries and timeouts in microservices?
A:

// Using Polly library
var policy = Policy
    .Handle<HttpRequestException>()
    .Or<TimeoutException>()
    .WaitAndRetry(
        retryCount: 3,
        sleepDurationProvider: attempt => 
            TimeSpan.FromSeconds(Math.Pow(2, attempt)),
        onRetry: (outcome, timespan) => 
            Console.WriteLine($"Retrying after {timespan.TotalSeconds}s"));

var response = await policy.ExecuteAsync(() => 
    httpClient.GetAsync("https://api.example.com/data"));

Q77: What is the Circuit Breaker pattern?
A: Circuit Breaker prevents cascading failures when a service is down:

- Closed: Normal operation, requests pass through
- Open: Service down, requests fail fast (no calls made)
- Half-Open: Testing if service recovered, allows test request
- Back to Closed or Open based on test result

Prevents repeated calls to failing services, reducing load on broken service.

Q78: How do you handle transactions across microservices? (Saga pattern)
A: Distributed transactions are problematic. Use Saga pattern:

  • Choreography: Each service listens to events and triggers next step
  • Orchestration: Central coordinator directs the flow
// Order → Payment → Inventory → Notification
// If Payment fails, compensation: Refund Order

Alternative: Accept eventual consistency, use compensating transactions.

Q79: How do you log and trace requests across microservices?
A:

// Correlation ID pattern
// 1. Incoming request gets/generates correlation ID
var correlationId = context.Request.Headers["X-Correlation-ID"];

// 2. Pass correlation ID to downstream services
client.DefaultRequestHeaders.Add("X-Correlation-ID", correlationId);

// 3. Log with correlation ID
logger.LogInformation("Processing order {CorrelationId}", correlationId);

Tools: Application Insights, Jaeger, Zipkin for distributed tracing.

Q80: What is API Gateway pattern?
A: API Gateway sits between clients and microservices:

  • Single entry point for clients
  • Request routing to appropriate service
  • Authentication/authorization centralized
  • Rate limiting, logging at gateway
  • Response aggregation (combining multiple service responses)

Examples: Azure API Management, Kong, AWS API Gateway.

Advanced Level

Q81: How do you handle authentication and authorization across microservices?
A:

// Option 1: Centralized (OAuth 2.0 / OpenID Connect)
// Gateway authenticates, passes token to services
services.AddAuthentication("Bearer")
    .AddJwtBearer(options =>
    {
        options.Authority = "https://auth-service";
        options.Audience = "my-api";
    });

Q82: Explain idempotency in microservices communication. (Commonly ignored)
A: Idempotent operations produce same result regardless of how many times called:

// Idempotent: Multiple calls safe
PUT /api/orders/1
{ status: "shipped" }

// Non-idempotent: Multiple calls problematic
POST /api/orders/1/increment-status
// Called twice = shipped twice!

// Solution: Idempotency key
POST /api/orders
Headers: { "Idempotency-Key": "uuid" }
// Duplicate request returns cached response, not duplicate order

Q83: How do you handle partial failures in microservices?
A:

  • Service A calls B: B timeout
  • Service A calls C: C success
  • Result: Inconsistent state

Solutions:

  • Bulkhead pattern: Isolate failures to specific component
  • Fallback: Return degraded response
  • Async compensation: Trigger rollback transaction
  • Eventual consistency: Accept temporary inconsistency

Q86: Explain the difference between Event Sourcing and CQRS in microservices.
A:

  • CQRS: Separate read and write models. Read model optimized for queries, write model for inserts.
  • Event Sourcing: Store events (state changes), not state. Rebuild state by replaying events.
// Traditional: Store current state
{ OrderId: 1, Status: "Shipped" }

// Event Sourcing: Store events
{ OrderCreated: 1 } → { PaymentProcessed } → { OrderShipped }
// Rebuild status by replaying events

Middleware

Basic Level

Q89: What is middleware in ASP.NET Core?
A: Middleware is a component that handles HTTP requests and responses. It forms a pipeline where each middleware:

  1. Processes incoming request
  2. Optionally calls next middleware via await next()
  3. Processes outgoing response
  4. Returns response

Think of it as an assembly line for HTTP requests.

Q90: How do you create a simple middleware?
A:

// Method 1: Inline middleware
app.Use(async (context, next) =>
{
    // Before
    Console.WriteLine("Request coming in");
    await next();
    // After
    Console.WriteLine("Response going out");
});

// Method 2: Class-based middleware
public class MyMiddleware
{
    private readonly RequestDelegate _next;
    
    public MyMiddleware(RequestDelegate next)
    {
        _next = next;
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        // Before
        await _next(context);
        // After
    }
}

// Register
app.UseMiddleware<MyMiddleware>();

Q91: What is the RequestDelegate?
A: RequestDelegate is a delegate that processes HTTP request:

public delegate Task RequestDelegate(HttpContext context);

Each middleware wraps the next RequestDelegate, forming the pipeline.

Q92: What is middleware ordering?
A: Middleware processes requests in registration order, responses in reverse:

Request:  MW1 → MW2 → MW3 → Handler
Response: ← MW1 ← MW2 ← MW3 ← Handler

Order matters! Example: Auth before Authorization.

Q93: What built-in middleware does ASP.NET Core provide?
A:

  • UseExceptionHandler(): Global exception handling
  • UseAuthentication(): Verify credentials
  • UseAuthorization(): Check permissions
  • UseRouting(): Match request to endpoint
  • UseCors(): Handle cross-origin requests
  • UseStaticFiles(): Serve static files
  • UseSession(): Session management
  • UseHsts(): HTTPS enforcement

Q94: What is short-circuit in middleware?
A: When middleware doesn’t call await next(), it stops the pipeline (short-circuits):

app.Use(async (context, next) =>
{
    if (context.Request.Path.StartsWithSegments("/admin"))
    {
        context.Response.StatusCode = 403; // Forbidden
        return; // Don't call next - short-circuit!
    }
    await next();
});

public class LoggingMiddleware

    {

        }
    }
}

Q102: How do you implement rate limiting middleware? (Commonly ignored)
A:

public class RateLimitMiddleware
{
    private readonly RequestDelegate _next;
    private readonly int _maxRequests;
    private readonly int _windowSeconds;
    private readonly Dictionary<string, List<DateTime>> _requestLog;
    
    public RateLimitMiddleware(RequestDelegate next, int maxRequests = 100, 
        int windowSeconds = 60)
    {
        _next = next;
        _maxRequests = maxRequests;
        _windowSeconds = windowSeconds;
        _requestLog = new Dictionary<string, List<DateTime>>();
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        var clientId = context.Request.HttpContext.Connection.RemoteIpAddress.ToString();
        var now = DateTime.UtcNow;
        
        if (!_requestLog.ContainsKey(clientId))
            _requestLog[clientId] = new List<DateTime>();
        
        var recentRequests = _requestLog[clientId]
            .Where(d => (now - d).TotalSeconds < _windowSeconds)
            .ToList();
        
        if (recentRequests.Count >= _maxRequests)
        {
            context.Response.StatusCode = 429; // Too Many Requests
            await context.Response.WriteAsync("Rate limit exceeded");
            return;
        }
        
        _requestLog[clientId] = recentRequests;
        _requestLog[clientId].Add(now);
        
        await _next(context);
    }
}

// Modern: Use built-in RateLimitingMiddleware (.NET 7+)
services.AddRateLimiting(options =>
{
    options.AddFixedWindowLimiter("fixed", opt =>
    {
        opt.PermitLimit = 100;
        opt.Window = TimeSpan.FromSeconds(60);
    });
});

app.UseRateLimiter();

Q103: How do you handle streaming responses in middleware? (Commonly ignored)
A:

app.Use(async (context, next) =>
{
    var originalBody = context.Response.Body;
    
    // Important: Some middleware needs direct access to body stream
    // Don't buffer if streaming file/content
    
    if (context.Request.Path.StartsWithSegments("/files"))
    {
        // Let streaming pass through directly
        await next();
    }
    else
    {
        // Only buffer for non-streaming responses
        using (var memoryStream = new MemoryStream())
        {
            context.Response.Body = memoryStream;
            await next();
            memoryStream.Position = 0;
            await memoryStream.CopyToAsync(originalBody);
        }
    }
});

Gotcha: Buffering middleware can break file streaming; check content type first.

public class ServiceDependentMiddleware
{
    private readonly RequestDelegate _next;
    // Singleton/scoped services injected via constructor
    private readonly ISingletonService _singletonService;
    
    public ServiceDependentMiddleware(RequestDelegate next, 
        ISingletonService singletonService)
    {
        _next = next;
        _singletonService = singletonService;
    }
    
    // Scoped services injected via InvokeAsync
    public async Task InvokeAsync(HttpContext context, 
        IScopedService scopedService)
    {
        var data = _singletonService.GetData();
        await scopedService.ProcessAsync(context);
        await _next(context);
    }
}

Rule: Singleton services in constructor, scoped in InvokeAsync.

Q105: What is middleware composition and pipeline ordering best practices?
A:

// Recommended order:
app.UseExceptionHandler();           // 1. Catch exceptions from all middleware
app.UseHsts();                       // 2. Security headers
app.UseHttpsRedirection();           // 3. Redirect HTTP to HTTPS
app.UseStaticFiles();                // 4. Static files (bypass MVC)
app.UseCookiePolicy();               // 5. Cookie handling
app.UseRouting();                    // 6. Determine endpoint (required)
app.UseCors();                       // 7. CORS (after routing, before auth)
app.UseAuthentication();             // 8. Verify user identity
app.UseAuthorization();              // 9. Check permissions
app.UseSession();                    // 10. Session (after cookie)
app.UseResponseCaching();            // 11. Cache responses
app.MapControllers();                // 12. Register endpoints
app.UseEndpoints(endpoints => ...);  // 13. Execute endpoint

// Mnemonic: SHAPE CAR
// S: Static files
// H: HTTPS redirect
// A: Authentication
// P: (Policies) CORS
// E: Exception handling
// C: Cookies/CORS
// A: Authorization
// R: Routing & Response handling

Summary Cheat Sheet

Clean Architecture

  • Layer dependencies point inward only
  • Use DTOs for API boundaries
  • Repository Pattern for data access
  • Specification Pattern for queries
  • CQRS for read/write separation

Singleton & Sealed Classes

  • Use Lazy<T> for thread-safe Singleton
  • Sealed class prevents inheritance + enables optimization
  • Prefer DI over Singleton pattern
  • Sealed methods prevent overriding in derived classes

ASP.NET Core Lifecycle

  1. Request → Middleware pipeline → Routing → Handler → Response
  2. ConfigureServices registers; Configure builds pipeline
  3. Scoped services per HTTP request (safe with DbContext)
  4. Middleware order critical: Exception → Auth → Routing → Endpoint
  5. IHostedService runs background tasks

.NET Core vs .NET Framework

  • .NET Core: Cross-platform, modern, faster, open-source
  • .NET Framework: Windows-only, legacy, deprecated
  • No AppDomains in .NET Core (simpler, less isolated)
  • Self-contained deployment bundles runtime with app

Microservices Communication

  • Synchronous (REST/gRPC): Simple but tightly coupled
  • Asynchronous (Messaging): Loosely coupled, eventually consistent
  • Service Discovery: Find available service instances
  • Circuit Breaker: Prevent cascading failures
  • Saga Pattern: Distributed transactions
  • Correlation ID: Trace requests across services
  • Idempotency Key: Safe retry semantics

Middleware

  • Pipeline processes requests in order, responses in reverse
  • Short-circuit by not calling next()
  • Singleton services in constructor, Scoped in InvokeAsync
  • Typical order: Exception → HTTPS → Static Files → Routing → Auth → Endpoint
  • Can branch/condition middleware with Map/MapWhen

Tips for Interview Success

  1. Understand the “why”: Not just what Clean Architecture is, but why it matters
  2. Provide code examples: Show you can implement, not just explain
  3. Discuss trade-offs: “It depends on…” shows nuanced thinking
  4. Mention commonly ignored aspects: Demonstrates depth (idempotency, scoped services, middleware ordering)
  5. Relate to real scenarios: “In my last project…” makes answers concrete
  6. Ask clarifying questions: Shows you think critically about requirements
  7. Discuss testing: Senior roles care about testability and maintainability
  8. Performance considerations: Mention TechEmpower, benchmarking, async patterns
  9. Security implications: Auth, CORS, input validation
  10. Operational concerns: Logging, monitoring, graceful degradation
